# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

## The shared contract

`contract/loom.schema.json` (JSON Schema draft 2020-12) is the single source of truth for the perception/decision messages exchanged between the body (`plugin/`, Kotlin) and the mind (`cognition/`, Rust). Both sides carry **hand-written** binding types, not code-generated ones, kept honest against the schema by conformance tests. Edit the schema first; then update both sides' types until their conformance tests pass again.

- Rust bindings: `cognition/crates/contract/src/lib.rs` (serde). Conformance: `cognition/crates/contract/tests/contract_conformance.rs`.
- JVM bindings: `plugin/src/main/kotlin/dev/loom/contract/Contract.kt` (kotlinx-serialization) + canonical `LoomJson` config. Conformance: `plugin/src/test/kotlin/dev/loom/contract/ContractConformanceTest.kt`.
- Shared fixtures: `contract/fixtures/valid` (must validate + round-trip byte-for-byte on both sides) and `contract/fixtures/invalid` (must be rejected by the schema). Fixtures are stored as compact JSON with no trailing newline; field order matches the internal-tag-first declaration order both serializers emit. Adding a contract case means adding a fixture in both dirs.
  Byte-for-byte round-trip depends on serde_json (ryu) and Java's `Double.toString` producing identical float text, which they do only for values both render the same way.
  Keep fixture float values away from anything needing exponential notation (e.g. `1e-7`, which ryu emits as `1e-7` but Java as `1.0E-7`); such a value would pass one side's round-trip test and fail the other's.

**Union wire tagging is internal.** `Trigger` is tagged on `event`, `Intent` on `action`, with the variant fields inlined. Rust uses `#[serde(tag = "...")]`; JVM uses `@JsonClassDiscriminator` (needs a file-level `@OptIn(ExperimentalSerializationApi::class)`). Empty variants (`Trigger.GoalReview`, `Intent.Idle`) are unit/`data object`, serializing to just `{"event":"goalReview"}` / `{"action":"idle"}`. Keep the two tag configs identical or the round-trip fixtures diverge.

The fixtures are also the wire: the mind's integration test replays every `perception-*.json` at a real socket, and the JVM transport test uses the `decision-*.json` bytes verbatim as responses, so the two runtimes meet at the fixture rather than at a mock on either side.

**`contract/body-control.schema.json` is a second, sibling contract, not part of this one.**
It is the Mineflayer player body's own wire, and it shares no binding types or dependencies with the perception/decision contract.
Eight operations at protocol generation 2: `handshake`, `status` and `shutdown` for the process's lifecycle, `sense` for one bounded reading of a player's scene and vitals, `eat` for one explicit meal, `moveTo` for one walk to a named place, `flee` for one flight from a named creature, and `halt` for one cancellation of whichever of those two is running.
**Adding the last three operations did not move the generation and adding one `MoveOutcome` value did, and the asymmetry is the rule rather than an inconsistency.**
The schema's own `ControlOperation` description is the authority: an *operation* is something a controller asks for, so a controller never meets one it does not have, and one a peer lacks is refused with `unknownOperation`; a value the *body* answers from is the body's to choose, so widening it hands a controller that agreed this generation a frame it cannot read, for a request it made in good faith and without having asked for anything new.
Refusing that frame is fail-closed rather than a misreading, but a broken round trip a peer cannot anticipate is exactly what agreeing a generation is for - so the operation set is the only part of a generation that may grow.
Moving a generation costs a sweep of every fixture in the corpus and of both runtimes' own spelling cases, and the suites now read the generation from their codec rather than writing it down, so the next move is one constant in each runtime plus the fixture bytes.
It is the active product body. `LoomPlugin.kt` wires `ProcessBodySupervisor`, `SocketBodyControlConnector`, `PlayerBodyPort` and `BukkitPlayerServerState`; the Villager adapter remains compiled but unused, with no compatibility switch.
The process on the far end is landed and runnable: `body/src/body.js` plus the `body/bin/loom-body.js` executable.
`body/README.md` owns the rules for both the contract and the process: read it before changing either, since the process's policy-free invariant, the derivation of its list bounds from `MAX_FRAME_BYTES`, its loopback-literal rule, its shutdown order and the whole of its movement policy all live there rather than here.
Movement is why the process loads two plugins outside its reporting table - `mineflayer-pathfinder` and Mineflayer's own `physics`, both through `bot.loadPlugin` from `src/movement.js`, a separate seam that leaves `loadInternalPlugins` off and the reporting list unchanged - and `src/movement.js`'s own header is the authority on the rules that follow from it, including why every one of the library's policy fields is set explicitly, why the policy is rebuilt per request, and why one accepted request owns the path and a second is refused rather than served.
`physics` is the sharp one and may not be moved into the reporting table: it steps, falls and writes the client's own position roughly once a second of nobody's asking, so `movement.js` holds both halves of it shut - `bot.physicsEnabled` false and every movement packet dropped at the client seam - unless one accepted `moveTo` or `flee` owns the path, taken where the route is handed to the library and released on the single `settle` every ending goes through, keyed on the same per-run token `body.js` records the asking connection against.
**The drop set is the position reports *and* the packets a control state writes, and reading it as the reports alone is the mistake this design has already made once.**
`bot.setControlState` writes an `entity_action` for `sprint` and a `player_input` or an `entity_action` for `sneak`, so a set of four report packets let an unasked `entity_action` out with nothing owning the path.
**A terminal event is not the end of the library's tick, which is the second seam and the durable rule to carry away.**
On the search-refusal path `monitorMovement` restores the best-effort partial route after emitting `path_update`, which makes its own empty-path early return false, and then reaches `bot.look`, `setControlState('forward', true)` and `setControlState('sprint', true)`.
The terminal callback therefore puts the packet gate into a drain state but does not answer: final position and control-deactivation packets may finish the current physics frame, while new control activations are dropped and the owner remains occupied.
Loom's later listener on that same `physicsTick` samples the completed displacement and live threat, applies the travel and deadline bounds, clears whatever route and controls the library left, and restores the facing held at the terminal boundary.
The first microtask after the physics frame then closes the gate, releases ownership and answers, after Mineflayer has written the final position.
`settle` still queues one repair ahead of the answer, keyed on the run token and conditional on the library actually holding a route, so an ending outside that normal listener order cannot leave state behind or clear a later request's path.
Both halves are needed and neither is enough: dropping deactivation leaves the server sprinting, dropping the final position leaves it one tick behind the report, and admitting activation lets a partial route continue after the terminal event.
That is why the packet drop is not a claim about who calls what: it holds against the library, against a plugin added later, and against the next version of either.
The one thing that cannot be scoped is the plugin's 50 ms interval, which it arms on `login` and clears only on `end`, so what a request scopes is what that interval *does* - and with none in flight it emits no `physicsTick`, steps nothing and writes nothing, which `test/movement.test.js` proves by counting ticks and packets across every ending.
A body the server left in mid-air therefore stays there until a request owns it, which is deliberate.
**One search, one call: the pathfinder's per-call slice is deliberately unbounded in production, and putting a number back on it is the mistake to know about.**
The library slices a search by wall clock and resumes the remainder on the next physics tick, and a resumed search is not the search it interrupted - `getPathFromTo` runs `postProcessPath` on every slice, which rewrites the `Move` nodes the A* context still holds in its open heap - so a resumed search can lose a goal it was one pop from and exhaust its graph instead.
That arrives as `noPath`, which was reported as `noRoute` for ground the body had walked most of the way across, and for a `flee` it is an agent told there is nowhere to run while a hostile closes.
It failed the movement suite about one run in nine on a loaded machine, and the slice was 20 ms against searches that expand a handful of nodes in single-figure milliseconds - so it measured the host and not the work.
`NO_SEARCH_SLICE` is therefore unbounded, which makes a resume unreachable by construction; the library checks the slice before the total budget in the same loop, so anything finite would have to be strictly greater than the budget to be unreachable, and unbounded is the only value that cannot be hit at all.
**`SEARCH_BUDGET_MS` (516) is now a synchronous event-loop stall and so a control-plane latency figure, not a search-generosity one**, and it is measured rather than chosen: a walk to the far edge of `MOVE_REACH_BLOCKS` visits 32 nodes in 12 to 30 ms, a flight at `MAX_RETREAT_DISTANCE` visits 301 and is the worst search that can *succeed* at 112 to 172 ms, and an unreachable destination at the full reach exhausts 6115 nodes in 1.8 to 2.9 s and up to 5.2 s on a loaded host - which is the stall the old 4000 ms budget permitted.
Three times the worst succeeding search is the smallest budget those measurements support; `movement.js` states them beside the constant, and `movement.test.js` measures the worst single search and asserts it against the budget so a slower search fails there rather than in world as a quiet control channel.
Every search call receives the smaller of that budget and the request time still remaining, because the request timer cannot run while the synchronous search owns the event loop.
The wrapper retains which ceiling it supplied: a pathfinder `timeout` under the body ceiling is `searchOverBudget`, while one under the request ceiling is `timedOut`; a search that returns another status after crossing the request deadline is also `timedOut` before that status can answer first.
**Budget exhaustion is `searchOverBudget` and never `noRoute`.** The library tells the two apart and so does Loom: `noPath` is the ground's answer and `timeout` is Loom's own bound stopping a search that learned nothing about the ground, and collapsing them is a lie in the one direction that kills agents.
A heavily loaded host can reach the budget on a search that would have succeeded - the same flight measured 1296 ms with sixteen busy processes on twelve cores, and even a ten-node search has been seen past it on a host oversubscribed that far while running three other suites - which is a fact a controller is told rather than one it is lied to about.
That is inherent rather than a defect: the bound is time and the thing bounded is work, the library offers no way to bound a search by nodes, and the honest answer on such a host is `searchOverBudget`.
So a suite may assert the *work* a search does wherever it can and the clock only where the clock is the subject, and a stress proof states the load it held under: `npm test` is deterministic through sixteen busy processes on twelve cores, and pushing further than that reaches the bound rather than a wrong answer.
No test may buy determinism with a clock production does not run: the suite drives every case, real route and wire alike, under the production numbers, and what makes it deterministic is the absent slice plus scenes whose *work* is bounded - the ground-refused case stands on a small platform so its search exhausts in a few dozen expansions rather than a chunk column's 256.
**And no test may assert *which* of a search's two endings a real search reached, because that is a race between a wall clock and a graph and the host decides it.**
The two facts that close the question are worth keeping: the widest search any request can produce is bounded, since the library prunes on `g + h > maxCost` and derives `maxCost` as the start node's heuristic plus `SEARCH_RADIUS_BLOCKS`, so `MOVE_REACH_BLOCKS` caps the graph at 6115 nodes and a wider world adds nothing past four chunk columns; and the *cost* of that same graph swings sevenfold with the block layout under it, measured at 447 ms with solid ground beneath the floor against 3064 ms with air beneath it.
A `flee` cannot beat that bound either, which is the trap to know about: its inverted goal makes the radius prune nothing, but the same inversion satisfies the goal at the first node further from the threat than the request's `distance`, and a threat far enough away to disable the radius is already further than any `distance` the wire allows - so the flight ends on its first pop.
So the split between `noRoute` and `searchOverBudget` is proven at the status seam, by handing the wrapper the library's own `path_update` status, and the budget is proven as an *upper* bound on the stall that holds whichever way the search ended.
Any scene the suite leaves bounded states its measured exhaustion time beside its node count, so no margin is left as an assumption.
**A node-count assertion belongs only where a search is certain to exhaust, and putting one on the widest search is a bound that cannot fail.**
Under the production budget that search is stopped at about a fifth of its 6115 nodes, so `visited <= 6115` is satisfied by a graph of any size at all - which is what it read as for one revision, comment and all.
The small-platform scene is where the pin bites, because an exhausted search visited every node it could build, so an *exact* count there says the search reached all of the ground and none of the air off it; the widest search's count is a recorded measurement rather than an assertion.
Its codecs are `body/src/protocol.js` (Node) and `plugin/src/main/kotlin/dev/loom/bodycontrol/` (JVM), kept in step by the shared conformance corpus under `contract/fixtures/body-control`, and `BodyControlBoundaryTest` pins that `dev.loom.bodycontrol` depends on nothing else in Loom.
That corpus has a **third** directory the perception/decision one does not, and it is the one worth knowing about.
`beyond-schema/` holds frames the schema *accepts* and both codecs refuse, because several of this wire's rules are relations between fields rather than shapes - a saturation no larger than the food level it sits in front of, inventory slots in strictly increasing order, an omission count reported only against a list something was in fact cut from.
Each such case is pinned from both sides at once and the two halves sit in different suites (`test/conformance.test.js` for the refusal, `BodyControlConformanceTest` for the refusal *and* that the schema really does admit it), so a case that in fact belongs in `invalid/` cannot sit there unnoticed.

**The active player path states hunger in vanilla's own terms.**
`sense` reports `bot.health`, `bot.food` and `bot.foodSaturation` as three separate facts, so a player body carries no `Metabolism` reserve and no food table of Loom's, and `eat` is `bot.equip` plus `bot.consume` with a full bar refused by the library rather than by arithmetic here.
`SelfState` now carries `health`, `food` and `saturation`; the unused Villager adapter projects its legacy reserve into those player-shaped fields only to stay source-compatible until it is removed.
Both operations are answer-only: there is no threshold, no target selection and no auto-eat plugin anywhere in `body/`, and no timer in the process starts anything - each either bounds a request a controller asked for or, in the one case the client library owns, does nothing at all until one is in flight - so a starving body with bread in its inventory does nothing at all until a mind names one slot.
An `eat` names the `sense` answer that offered the slot as well as the slot, so a handle is scoped to one round trip on one control connection. `PlayerBodyPort` retains that exact connection through cognition so the meal and movement answer the sense that minted their refs.
The body keeps a bounded memory of recent answers rather than a lookup in something unbounded, so a superseded one is `senseForgotten` rather than a growing map; the agent half of the isolation is structural instead, since one process drives exactly one body.
A round trip is a connection as well as a request id, so an entry in that memory names both, and getting this wrong is not a scoping nicety but a wrong meal.
The duplicate-id guard is per control connection - a request id is the controller's own name for its round trip and two controllers share no numbering - so two of the connections the process allows may each sense under one id; keyed on the id alone the second answer replaced the first, and an eat from the first connection then ate a stack its own sense never offered and reported it as `eaten` rather than as the `slotChanged` the slot in fact was.
The bound stays on the whole memory rather than per connection, so no number of peers can make it grow, and a handle a connection never held is the `senseForgotten` a superseded one already earns, which is why nothing on the wire changed for it.
A player-body creature offer retains Mineflayer's exact entity object beside its numeric id, because that id may be reused after the creature leaves.
The bounded sense memory marks offers dead on `entityDead`, and each active flight also listens for that exact object until settlement, because Mineflayer can leave a dead object in `bot.entities` with `isValid` unchanged until a later destroy packet.
`body/src/eating.js`'s header owns the ordering of the eight closed outcomes and why the slot is re-read at apply time.

## The body port

`plugin/src/main/kotlin/dev/loom/body/BodyPort.kt` is the inbound port the rest of Loom uses to give an agent a physical presence.
Its surface is exactly four capability areas - lifecycle, actuation, perception, and the server-tick hook - and it should stay that size.
Only Loom domain and contract types appear in its signatures; no engine type and no world handle crosses it, which is what makes the body flavor replaceable.

The product adapter is `dev.loom.body.player.PlayerBodyPort`. Process and socket waits run on its bounded I/O pool, while every lifecycle, ref, witness and journal mutation returns through the server-main-thread executor. Its startup order is registration -> child launch -> control handshake/status -> server presence -> `spawned`; every failed partial startup stops the child before answering. Its shutdown order releases held sense sessions first, stops the child, then records `despawned` only after cleanup succeeds. A failed cleanup is `FAILED`, never a successful despawn.

**`notReady` is not evidence that the process is gone.**
The body process refuses a second movement while one accepted request owns the path. `PlayerBodyPort` must record that as `CONTROL_NOT_READY` while the child remains alive and ready; treating it as a disconnect kills a healthy process under ordinary concurrent cognition. Only an actual process/socket loss can produce `DISCONNECTED`, and only `PlayerServerState.isDead` can produce `DEAD`.

**Threat refs and threat identity have different lifetimes.**
The body-control `sense` entity ordinal remains request-local because `flee` must name the exact answer it came from. Threat debounce needs identity across senses, so `BukkitPlayerServerState.subjectsOf` correlates each client observation to the nearest same-kind server entity within its bounded tolerance, consuming each server candidate once. The server UUID is used only for debounce; an uncorroborated observation stays request-local rather than being guessed onto a creature.

`dev.loom.body` is engine-free by rule, and the movement policy (`Navigation`), perception bound (`PerceptionBound`), mortality rule (`Mortality`), and world-loading footprint (`WorldFootprint`) live there so they are unit-testable without a server.

Two design constraints are load-bearing, not stylistic:

- **Minecraft may find a route; it may never choose a goal.** Bodies walk with the engine's own ground navigator, so an agent sent somewhere goes round a wall and up a step instead of pressing into it - but every request carries a target the mind named, nothing below the port invents one, and an out-of-range target is refused and recorded rather than clamped, because a clamped target would be a goal Loom chose. A refusal also *drops the route the body was already walking*, because a route left running would keep the body moving toward the previous target and put `moved` records after the `rejected` one - which anything derived from the event log reads as movement Loom authorised; `NavigationPolicy.route` therefore carries the verdict out rather than only reporting it, and the rule is about the *outcome* rather than about whose bound was hit, so a refusal variant added later is covered without being named.
  That last part is load-bearing on the case a reader would not expect: a granted request still reaches an engine with refusals of its own, and a ground navigator will not search while its body is off the ground - stepping down a slope, or mid-jump over a one-block rise - so it answers a perfectly reachable target with no route at all, on a branch that never touches the navigator.
  The body keeps zero vanilla goal selectors and no brain, and the build enforces both halves: `BodyBoundaryTest` fails if anything under `dev.loom` calls `addGoal` or `registerGoals` or touches either selector field, and equally if anything calls `getBrain` or delegates upward to `customServerAiStep`, or the body stops overriding both of that hook's overloads - which is a stronger statement than any runtime check could make (constructing a body needs a real `Level`).
  Read `dev/loom/body/Navigation.kt` before changing what a body may be asked to do.
- **`BodyPort.tick` drives actuation only and must never invoke cognition.** Cognition is event-driven by construction: the contract's `Trigger` deliberately has no per-tick variant.

**`FOLLOW_RANGE` is a walk budget, not a reach, and reading it as a reach is the mistake this design has already made once.**
`PathFinder` spends the attribute on the *length of the route*: it abandons a partial route as soon as the distance walked along it reaches that number, and expands no node further than it in a straight line from the start.
So a body sent across open ground may go the whole budget, while a body that has to go round something pays for the detour out of the same money - and, worse, a request the budget cannot afford comes back as a *best-effort* route with `canReach` false rather than as nothing, so the shortfall arrives as a body pressed against a wall.
`PATH_REQUEST_REACH_BLOCKS` is therefore half of `BODY_FOLLOW_RANGE_BLOCKS` (8 of 16), and `NavigationTest` pins that what is left after the reach is at least the reach again.
An in-world run found this the hard way: a body three blocks from a nine-block wall, sent seven and a half blocks to the far side, was given a four-node route that walked it into the wall and stopped, because the way round was eighteen blocks of walking.
Two consequences worth knowing before changing either number.
A body can be sent to far less than it can see - perception reaches twenty-four blocks, the reach is eight - so a target the mind saw and named may be refused, and the refusal is recorded; walking there in stages is the agent's business until an intent exists for it.
And a wall long enough that the way round it exceeds the budget is still refused in effect, as a best-effort route: the shape of obstacle a body can round is bounded by the budget, not by the reach.

**The engine moves the target before it searches, so what a route reached is not what the mind named.**
`GroundPathNavigation.createPath` adjusts the named block first: a block full of air becomes the ground *below* it, and a solid block becomes the first non-solid block *above* it.
Only the adjusted block is searched for, and `Path.canReach` and `Path.distToTarget` both answer about *that* block, which is why a body sent three blocks into the ground was first recorded as reaching its target with nothing left to walk.
The applied record therefore states two facts about two targets: `reaching what it searched for` is the engine's verdict on its own adjusted block, and `ending N blocks from it` is Loom's own straight-line measure from the end of the route to the block the mind named, taken with the same `blocksApart` the reach is measured with.
So a complete route that ends three blocks away now reads as exactly that.
Do not put `Path.distToTarget` back: it is the shortfall against the wrong target, and it reads as `0.00` in precisely the cases where the body did not go where it was sent.
Both facts in that measure are *blocks*, so both sides of it are one: `blockAt` (engine-free, in `Navigation.kt`) is the only way to turn a `BodyLocation` into a `BodyBlock`, and the block the navigator is asked for, the block the record names and the block the shortfall is measured against are all that one answer.

**`blockAt` floors, and truncating toward zero instead is a bug this already had.**
Truncation is floor only for a non-negative coordinate, and the walk path hides that completely: the contract's `moveTo` carries three whole numbers, on which the two roundings agree.
The flight path does not, because `LandRandomPos.getPosAway` answers with `Vec3.atBottomCenterOf` a block it scored - x and z carry half a block - so at a negative x or z a `toInt()` named the block one step nearer the origin, which in a scene where the threat is toward the origin is one step back toward the threat, handing away up to 1.41 of the two blocks of `MEANINGFUL_SEPARATION_BLOCKS` gain `chooseRetreat` had just insisted on.
Nothing errored and no record contradicted it; `NavigationTest.aBlockIsFlooredRatherThanTruncated` and `aWholeTargetNamesTheSameBlock` are what pin it now.
The offered position is deliberately kept as the bottom centre for `chooseRetreat`'s arithmetic, because that is where a body actually stands on arriving, so the step and the gain are measured against the truth rather than against a block corner.
`BodyBlock` is a separate type from `BodyLocation` for that reason: a location is a measurement and a block is not, and keeping them apart is what stops a second rounding appearing at a call site.

**Loom's token bucket bounds only the searches Loom itself asks for, and the engine asks for others.**
`ServerLevel.sendBlockUpdated` (`ServerLevel.java:1686`) runs on every block change whose old and new collision shapes differ, walks `navigatingMobs` - which `onTrackingStart` (`ServerLevel.java:2543`) fills with *every* `Mob` in the world, Loom bodies included - and calls `recomputePath` (`PathNavigation.java:82`) on each navigator whose `shouldRecomputePath` (`:439`) says yes, which is any body with a live route whose changed block is near it.
That is a full A* outside `NavigationPolicy`, and the tick path is not search-free either: `recomputePath` throttles itself to one per twenty game ticks and otherwise sets `hasDelayedRecomputation`, which `PathNavigation.tick` (`:257`) then acts on.
So the earlier claim that a *request* is the only search and the tick advances a waypoint index and searches nothing was wrong once Loom started putting a path on the navigator; before this change no Loom body ever had one, so `shouldRecomputePath` was never true.
What still bounds a recompute is per body rather than per tick: the same 256-node budget the follow range fixes, and the fact that it fires only for a body already walking near a changed block.
Paper's `updatePathfindingOnBlockUpdate` gates the whole path and defaults to true.
`BODY_FOLLOW_RANGE_BLOCKS` (16) bounds all of it: besides the walk budget above, the engine reads the attribute at navigator construction to fix the node budget at sixteen nodes per block, and again per request as the half-extent of the region the search reads.
`NavigationPolicy` is server-wide rather than per agent for that reason: a hundred agents *deciding* to walk in the same tick cost the same as `DEFAULT_PATH_REQUESTS_PER_TICK` (4), and the fifth *movement* request is refused *and recorded* so a run that outgrows the budget says so in its own log instead of merely feeling sluggish.
Movement is not the only thing spending it now: a threat scan's reachability probe pays into the same bucket (see the vigilance paragraph below), and one sweep probes every living agent in the *same* tick, so the contention below is reached by standing still as well as by deciding to walk.
A probe's refusal is the one `OverBudget` nothing records: it arrives as a sighting stating `reachable` false, which reads as ground the body cannot walk to rather than as ground nothing asked about - a bound on the mind's evidence and never on whether the sighting fires, which is the other reason the tier `importanceOf` prices leaves `reachable` out.
The budget does not accrue, and only a granted request spends a token, so a tick full of out-of-range targets leaves the budget for the requests that could have used it.
Note before tuning that number that an `OverBudget` refusal stops the prior route like any other, so with more agents deciding in one tick than the budget serves, the excess lose the route they were already walking even when the target they named is unchanged and reachable.
A *walk* refused that way is simply lost, and nothing retries it before its next goal review; a *flight* is not, because there the same refusal is `RetreatAttempt.PendingBudget` and the retreat is held rather than ended - see the routing-seam paragraph below.
Nothing retries, so those agents stand still until their next goal review, up to a whole `DEFAULT_GOAL_REVIEW_CADENCE_TICKS` later - which makes the bucket a behaviour knob under contention and not merely a throughput one.
The engine's own refusal is under the same stop and is the least defensible case of it, because there the bound is not real: a body momentarily off the ground - mid-jump over a one-block rise, or stepping down a slope - fails `canUpdatePath`, so `createPath` answers a perfectly reachable target with no route, and the agent loses a legitimate route *and* the token it spent, again with nothing retrying before its next goal review.
Distance is a straight line, and all three axes count, because the bound it is measured against is a walk and a walk is never shorter than the straight line; a per-axis maximum reads the corner of a cube as being one side away and promises a detour that is not there.

**The hold radius is derived from everything that reads past the body, and getting that wrong fails silently.**
A path search reads the world through `PathNavigationRegion`, which never blocks and substitutes an *empty* chunk for any that is not loaded - so an unloaded chunk reads as **air**, and the search answers confidently about ground it never looked at.
An entity query is the same shape of failure with a different symptom: a chunk that is not loaded holds no entities, so a perception reaching into one is not an error and not an empty answer either but a *quiet scene*, which is the one reading a survival run must never be given.
`holdRadiusChunksFor` therefore derives the `WorldFootprint` radius (2 chunks, 25 per lone agent, up from 9) from the **widest** of its readers - the follow range plus the engine's own hardcoded 8-block region margin, and `PERCEPTION_RADIUS_BLOCKS` - and `NavigationTest` pins the derivation against both, so raising either one cannot leave the hold behind.
Both reach exactly 24 blocks today, which is precisely the coincidence that made the perception half invisible until the derivation took it in: the radius was covered by accident and nothing related the two numbers.
Note that the search region is 24 blocks around the body, wider than anywhere a body can be sent: the hold has to cover what a search *reads*, not where it may go.
The chunk-edge case needs no allowance of its own; `Navigation.kt` carries the proof.
Note that the approved design document states the rule as `radiusChunks * 16 >= followRange + requestRange + 16`, which conflates `createPath`'s *accuracy* parameter with the region *range* parameter and so has no single arithmetic reading.
The engine-derived form is the one correctness depends on, and `theHoldCoversWhatASearchReads` and `theHoldCoversWhatAPerceptionReads` are the only tests that pin it; reason from those rather than from the design document's sum.

**Pathfinding malus is a survival decision, not a tuning knob**, because Loom is permadeath and no flight escapes a hazard: `Intent.Flee` runs from a creature a mind named, and nothing runs from the fire or the water a route walked into.
The whole policy is the pure `loomPathfindingMalusFor`, which `PathfindingMalusTest` reads without a world; the entity only applies it, over every `PathType` so a type the engine adds later cannot be missed.
Three prices, ordered the way the danger is and every one of them positive: standing *in* fire costs twice the walk budget, the blocks *beside* fire and the wither roses and pointed dripstone of `DAMAGE_CAUTIOUS` - which vanilla charges *zero* for - cost the whole walk budget, and the shore keeps the engine's own 8.
A step through any of them therefore costs more than any detour that could complete, and a body already standing in or beside one is not stranded.
The cost of pricing rather than forbidding is accepted rather than welcomed: a route may step through fire or a wither rose where the only way round is a long detour.
**Water is impassable, because this body has no swim mechanism at all.**
`Villager`'s `setCanFloat(true)` is a node-evaluator setting that makes the *pathfinder* willing to enter water and has nothing to do with buoyancy; a villager's buoyancy is the brain behaviour `Swim`, and `customServerAiStep` never ticks the brain.
So a body walked into two blocks of water sinks, stops advancing its route, and drowns on a route Loom itself chose.
Rivers are deliberate walls from every tile a body can stand on that the engine does not itself price negative.
From a tile the engine *does* price negative - a body already in water, in lava, in a fence, or in a sweet berry bush - the engine's own escape rule opens every neighbour including water, by design; that is inherent rather than a gap, because the negative water price is both what makes a river a wall and what lets a submerged body path out.
**Water is the only type Loom may price negative.**
What unlocks water is a negative *start* node whatever made it negative: `getStartNode` copies the malus onto the start node with no sign gate, `isNeighborValid` accepts every neighbour of a negative node, and `PathFinder` adds the malus to `g` unchecked - so a second negative type costs `1 - 1 = 0` per water step against `1` for dry ground and makes water the *cheapest* ground on the map. Pricing one more thing impassable does not build a second wall; it takes the first one down.
Both readings of "under the body" reach it, which is why the rule cannot be narrowed to adjacency: `checkNeighbourBlocks` answers `WATER_BORDER` for an ordinary dry tile within one block of water and `DAMAGE_CAUTIOUS` for one beside a wither rose, and it returns on the first matching neighbour in `i,j,k` order, so a dripstone one block west outranks a pond one block east; while `getPathTypeStatic` answers `DAMAGE_FIRE` for a tile whose block *below* is burning, and `NodeEvaluator.isBurningBlock` counts a magma block and a lit campfire as well as fire and lava.
An impassable `DAMAGE_CAUTIOUS` opened water from a tile merely near both, and an impassable `DAMAGE_FIRE` opened it from any magma block.
`PathfindingMalusTest.waterIsTheOnlyImpassableType` and `nothingUnderABodyIsImpassable` pin it; note that both pin the *policy*, since running the engine's own search needs a real `Level`.
The malus alone does the work, so `canFloat` is left on: `WalkNodeEvaluator.findAcceptedNode` builds a node only for a malus of zero or more, `isNeighborValid` rejects the blocked node the descent scan does build, and nothing in the accept path lets `canFloat` override either - while leaving it on helps a submerged body, whose start node `getStart` lifts to the surface.
Note that `PathFinder` itself never checks the sign and would treat a negative malus as a *cheaper* node, so the impassability is `WalkNodeEvaluator`'s and not the pathfinder's.
Nothing Loom prices strands a body: standing in fire, beside fire, on dripstone or on the shore all give a positive start node, so `isNeighborValid`'s first clause admits every neighbour on its own, and a body in water has the negative one so the second clause admits them instead - though nothing can swim it out.

Three owed follow-ups.
There is no `pathEnded` record yet: a route ending is visible only in the next `moved` detail, and a body that got stuck while already stationary produces no record at all.
The reach is not yet stated in the agent brief the mind is given, which matters more now that it is a third of the perception radius - a mind that knew it would ask for somewhere eight blocks off and walk again, instead of naming what it can see and being refused.
And the engine's own `recomputePath` searches are not budgeted in total, only bounded per body, which is deliberately left for a follow-up rather than fixed here.

**An observation is a bearing, a height and a line of sight, and every one of those facts is the engine's own answer rather than Loom's geometry.**
`BodyPerception.kt` reads them from `Direction.getNearest` with the vertical delta zeroed, from the two entities' `y`, and from `LivingEntity.hasLineOfSight`, which is a real ray trace: `visible` false means the body knows something is there and cannot see it, which is the difference between a threat behind a wall and one in the open.
**`visible` is a line, not a field of view, and the brief has to say so.**
The body's facing is never consulted and there is no cone: everything within the radius is equally known, ahead or behind, and nothing has to turn to look.
Left unsaid, "whether you can actually see it right now" reads to a model as human sight, and an agent then believes it can be surprised from behind or that its surroundings list is only what lies in front of it - so `AGENT_BRIEF` states it outright, `prompt.rs`'s `the_brief_says_in_sight_is_a_clear_line_and_not_a_field_of_view` pins the wording, and `every_tier_names_the_same_generation_of_the_brief` pins that all three `*_PROMPT_VERSION` constants moved together, since the brief is shared by every tier.
Bearing is horizontal on purpose and height is reported beside it, because a thing on a cliff is not reachable by walking toward it.
Candidates are gathered within `PERCEPTION_RADIUS_BLOCKS` (24) and then cut to `PERCEPTION_MAX_OBSERVATIONS` (16), both stated in `PerceptionBound.kt` and reached through `bodyPerceptionBound()` rather than written down in the adapter, because the radius has a second reader - the hold above derives from it, and a literal copy here is a copy the hold can fall behind.
The cut is applied to the *entities* before anything is described, so nothing is described that the count bound then drops.
**A candidate's distance is measured once and carried.**
`PerceptionBound.nearest` returns a `Measured` per survivor, so eligibility, the sort order and the distance the `Observation` reports are all one reading rather than three: the engine's own reading is a three-dimensional square root, and in a world where everything is moving three readings of one entity can disagree, which would let an observation report a distance the bound did not admit it for.
Ties keep candidate arrival order (`sortedBy` is stable), because the same scene has to render the same prompt.
The prompt's own `MAX_OBSERVATIONS` (24) stays the final bound on what reaches a model, and it is deliberately looser than what the body sends.
**A cut is stated, never silent, and the mind is told the whole of it.**
`PerceptionBound.nearest` is the only place that can still count what it dropped, so it returns a `Bounded` carrying the omission as well as the list, and that count rides *inside* the perception as `Perception.surroundingsOmitted` rather than beside it - which is what let the JVM's `CapturedPerception` wrapper be deleted, and why the `perceived` record ("N more nearby not reported") and the prompt the mind was given read the same field and cannot state different omissions for the same moment.
The prompt states the **sum** of that count and its own `MAX_OBSERVATIONS` cut, because the body's figure is about things that never reached the wire while the cap is measured against the list that did, so each bound is counted exactly once.
The field is required and non-negative on both sides, and a nonsense negative arriving off the socket is coerced to zero rather than allowed to subtract from the cut this side made for itself.
A crowded scene trimmed to the bound and recorded as a bare observation count would read afterwards as a quiet one, which is the reading a survival run must not be given.
A decision may *name* one of those observations, because a living one carries a `ref` and `Intent.Flee` resolves it - see `EntityRefs.kt` for the one-agent, one-request window that makes a handle mean something, and the flight section below for what consumes it.

**A ref window is bounded by the round trip it belongs to, never by a count of the perceptions that came after it, and `RequestWindow.kt` is the whole rule.**
It used to keep an agent's newest two requests, which is a bound on *traffic* rather than on the thing a handle is for - and traffic is exactly what a survival run generates: `senseThreat` reads the world every `THREAT_SCAN_CADENCE` for every living agent, so two earned sightings inside one round trip evicted the goal review whose decision was still in flight.
An agent both hungry and hunted therefore had its answer refused for naming a handle no request still held - a flight as `retreatThreatForgotten` about a threat that perception did name, and a meal as `eatSlotForgotten` about a stack it did offer, the agent starving with food in its hand.
So a window now closes when its decision is dealt with (`RequestRefs.settle`, called from `NmsEntityBodyPort.apply` for a refusal as well as an acceptance) or `REQUEST_REFS_LIFETIME_TICKS` (800) after the perception was handed out, whichever comes first; `MAX_REQUESTS_IN_FLIGHT_PER_AGENT` is a safety valve for an agent whose decisions never come back, not the ordinary rule.
The lifetime is a body-side constant in *ticks* because `dev.loom.body` may not see `dev.loom.mind`, and it has to outlast the bridge deadline a decision is allowed - 30 s, 600 ticks - or Loom would refuse handles it had promised to answer; `CognitionSettingsTest` pins that relation from the side that can see both.
**The ceiling is derived, and the bound it is derived from is not the debounce.**
It was once a written-down 32 justified by `THREAT_DEBOUNCE_TICKS`, and that is the wrong bound by five times: a debounce is a floor on repeats of an *unchanged* threat, and `ThreatWatch.mayLookAgain` deliberately re-fires inside it whenever a hostile crosses a line of sight or comes inside `PIVOTAL_THREAT_DISTANCE_BLOCKS` - which an ordinary mob pathing round a fence does on every scan.
So the fastest a perception can reach one agent is `FASTEST_PERCEPTION_CADENCE_TICKS` (20, restating `THREAT_SCAN_CADENCE`), the ceiling is the lifetime divided by it plus two, and the two numbers that used to be related only by coincidence - the margin was two requests, guarded by nothing - now follow the lifetime by construction.
`CognitionSettingsTest` pins the restated cadence against `THREAT_SCAN_CADENCE`, and `EntityRefsTest` drives a whole lifetime of earned sightings at that cadence against a goal review whose decision is still in flight.
**A window is opened only for a perception a mind was actually given, which is why minting is separate from remembering.**
Almost every threat scan's sighting is suppressed and reaches no mind at all, so `EntityRefs.mint` / `InventoryRefs.mint` hand back bindings that resolve to nothing, `captureScene` mints, and `BodyScene.perceptionOf` - the one place a perception is handed out - commits both stores together through `RequestRefs.remember`.
Both kinds at once is the invariant rather than tidiness: one perception carries creature handles and slot handles, and a request whose creatures were remembered and whose slots were not would resolve a flight and refuse a meal off the same perception.
`threatsIn` therefore resolves a candidate's creature from the scene that minted the handle rather than from the store, which does not hold it yet; the agent and the request the store would have checked are the scene's own either way.

**Running away is routing, so it goes through the one routing seam and inherits every bound already on it.**
`Retreat.kt` is the engine-free half - the speed, the search box, which offered spot is worth taking, and what it means when there is nowhere to go - and `BodyNavigation.fleeFrom` is the two engine calls: `LandRandomPos.getPosAway` for somewhere near the body and away from the threat, then the same `NavigationPolicy.route` a walk uses.
Nothing about a flight widens a bound: it pays for the same per-tick search token, is refused past the same `PATH_REQUEST_REACH_BLOCKS`, walks the same node budget, pays the same hazard and water prices, and loses its route on any refusal.
The only difference from a walk is `FLEE_SPEED_MODIFIER` (0.8 against `WALK_SPEED_MODIFIER`'s 0.5), which is why `BodyWalker` and `LoomBodyEntity.followRouteTo` take the speed as a parameter rather than reading a constant.
**The search box has to fit inside the reach, or Loom refuses retreats it chose itself.**
The far corner of `RETREAT_SEARCH_HORIZONTAL_BLOCKS` (5) in both axes plus `RETREAT_SEARCH_VERTICAL_BLOCKS` (2) up is 7.35 blocks, and `RetreatTest` pins that against the reach (8) - widening either search bound without widening the reach would turn retreats into out-of-range refusals, and only on the diagonals, which is the shape of bug an in-world run finds late.
Vertical is small for the same arithmetic: height counts in full against the reach, so every block of climb is a block of horizontal retreat given up.
**Which of the ground's answers is worth walking to is Loom's, and one answer is not enough to choose from.**
`LandRandomPos.getPosAway` scores random *blocks* for standability and never asks the navigator, so sampling it costs block probes and not path-search tokens - which is what lets `fleeFrom` ask `RETREAT_SEARCH_ATTEMPTS` (4) times and still route once.
`chooseRetreat` then keeps only a spot at least `MEANINGFUL_RETREAT_BLOCKS` (3) off, inside the reach, and at least `MEANINGFUL_SEPARATION_BLOCKS` (2) further from the threat than the body already is, and takes the furthest of those from the threat (`maxByOrNull`, so a tie keeps the order the ground offered and the same scene replays the same).
Asking once was fatal: an in-world run took the search's single answer 0.71 blocks away, walked a two-node route, and stood still while a zombie closed seven blocks and killed the agent.
Distance covered is not distance gained, which is why the gain is its own bound - and it asks for less than the step, because a partly sideways retreat is still worth taking.
**A flee names a creature, not a place, so it resolves through the request-scoped refs and can be refused five ways.**
`retreatFrom` asks the port's `EntityRefs` what the handle means and then looks for that creature *in the body's own level*; `refusalFor` is total over `RefResolution`, and `RetreatRefusal` keeps five distinct facts apart - the ref window passed (`ThreatForgotten`), the request never named it (`ThreatUnnamed`), it is dead or despawned or in another dimension (`ThreatGone`), the ground offered nowhere (`NoRetreat`), and it offered only spots underfoot or no further away (`NoMeaningfulRetreat`).
The last two are kept apart because they are opposite facts about the run: a body walled in had nowhere to stand, and a body in the open had plenty and none of it helped.
The three absences collapse into one refusal deliberately: a same-level `getEntity(uuid)` cannot tell them apart, and a position in another dimension is a number with no meaning where the body is standing.
An intent with no `requestId` resolves against no request and so reads as `ThreatForgotten`, which is honest - no request of that agent's ever named the threat.
Every refusal stops the body before answering, for the same reason a refused move does: a route left running would put `moved` records after the `rejected` one and read as movement Loom authorised.

**One accepted flee is a state the body keeps, not one hop, and the tick is what carries it on.**
`ActiveRetreats` (engine-free, `dev/loom/body/ActiveRetreat.kt`) holds at most one retreat per agent as the threat's `UUID` and the tick of the last attempt, and decides everything about a continuation: the threat is checked before the route, a live route is left alone, and a hop is asked at most once per `RETREAT_RETRY_CADENCE_TICKS` (10).
`RetreatDrive` (`dev/loom/body/nms/RetreatDrive.kt`) is the two engine reads and the one engine call that state needs, driven from the *actuation* branch of `NmsEntityBodyPort.tick` - so a flight costs a path search out of the same per-tick bucket a walk pays into and never a model call, which is what makes running away something an agent keeps doing between goal reviews.
`BodyBoundaryTest` forbids `dev.loom.body..` from reaching `dev.loom.mind..` at all, so the tick cannot invoke cognition even by accident.
An in-world run died of the absence of all this: one hop, arrival, then four seconds standing still while a zombie closed ten blocks.
**A ground navigator will not search while its body is off the ground, so a flight asks `onGround()` before it spends anything.**
`createPath` answers a perfectly reachable retreat with no route at all mid-air, and a body being hit is off the ground, so the same run lost a whole flight and the model call that decided it.
`fleeFrom` therefore returns `RetreatAttempt.Grounding`, which stops the old route (a flight is not carrying on with it) and *keeps* the retreat to ask again at the cadence.
That is reported as an `IntentOutcome.Accepted`: a flight waiting to start is not a flight that never happened, which is exactly what the log said about an agent that was in fact fleeing.
**A refusal at the routing seam is `Unrouted`, never `Refused`.**
A target past the reach and an engine that offered no route are answers about a *route*; the five `RetreatRefusal`s are answers about a *threat*.
Both end the retreat and both leave an already-stopped body, but a run that could not tell them apart could not say whether its agents were cornered or merely over budget.
**A tick whose search budget was already spent is not an answer at all, and ending a flight there is the same death arriving through Loom's own bookkeeping.**
Nothing was searched for, the target the mind named is unchanged, and it is reachable on the very next tick - so `PathRequest.OverBudget` is `RetreatAttempt.PendingBudget`, which is retained exactly as `Grounding` is: the prior route is stopped, the agent is told its flight was accepted, and the next attempt comes at `RETREAT_RETRY_CADENCE_TICKS` rather than from another decision.
Ended instead, the agent would stand still with a hostile on it until its next goal review, up to a whole `DEFAULT_GOAL_REVIEW_CADENCE_TICKS` later, and the record would say `retreatFailed` about ground that had never been asked.
It is a distinct tag (`RETREAT_PENDING_BUDGET`) rather than folded into either neighbour, because "waiting for a token", "waiting for the ground" and "the ground offered nothing" are three different facts about a run.
Reading the verdict is what `NavigationPolicy.routing` exists for: `route` delegates to it and keeps the stop rule in one place, because re-implementing request-then-walk in the adapter to get at the verdict would give that rule a second copy to drift.
**Supersession is keyed on an intent that was accepted *and* actually drives the body**, not on acceptance alone and not fired before applying one.
An intent the body refused took nothing over, so an unsupported `say` cannot end a flight the mind never meant to end, and a refused move leaves the retreat to re-route at its own cadence.
And an accepted intent that displaces nothing is not a supersession either: `Intent.Eat` is instantaneous and touches neither the navigator nor the position, so on acceptance alone it ended a live flight, the route already issued ran out, and the agent stood still with a hostile on it until its next goal review.
`takesTheBodyOver` in `ActiveRetreat.kt` is that rule, total over `Intent` so an intent added later has to say which it is rather than inheriting the answer that ends flights; `Flee` answers `false` there because a later flight replaces the threat through `ActiveRetreats.attempted` rather than ending a retreat that is still running.
Every transition is one `retreating` record with one of `EventTag`'s ten retreat tags, written once and never per tick - a flight held for the ground says nothing a second time, because the attempt that put it there already did.
**`RETREAT_FAILED` is the predation count, so only the ground's refusals may be filed under it.**
`tagOf(RetreatRefusal)` in `Retreat.kt` is total over the five refusals and maps only `NoRetreat` and `NoMeaningfulRetreat` there; `ThreatGone` takes `RETREAT_THREAT_GONE` - the same tag the continuation path's `ThreatStanding.GONE` already ends on, so one fact does not get two opposite tags depending on which path reached it - and the two ref refusals take `RETREAT_THREAT_FORGOTTEN` and `RETREAT_THREAT_UNNAMED`.
Reading them all as failures said "could not run from a threat, and is still in range of it" about an agent whose zombie had burnt to death, and inflated the one number a survival run reads for predation with decisions that were never about the ground at all.
`ActiveRetreatTest` is the whole of what a tick may ask; the engine half needs a live `Level` and is only provable on a real server.

**A threat interrupts cognition, and the whole rule for when is `ThreatWatch.kt`.**
Hunger is slow and the scheduled goal review is a fine place to notice it; predation is not, and an in-world run watched a zombie kill an agent whose every perception still said `goalReview`.
So a hostile in view earns a `Trigger.ThreatSighted` at once, and the two opposite failures bound everything else: never firing early kills agents mid-cadence, and firing every tick a zombie stands there is a frontier model call twenty times a second.
`VILLAGER_HUNTERS` is named by the engine's own entity description id rather than by class, which is why `zombie_villager` is in it: it inherits Zombie's target goals rather than declaring its own.
A first sight fires immediately, and after that only on `THREAT_DEBOUNCE_TICKS` (100) or on a change that alters what the agent should do - stepping out from behind a wall, or crossing inside `PIVOTAL_THREAT_DISTANCE_BLOCKS`.
The free tests run before the reachability probe on purpose, so a threat in view for a minute costs one path search per window and a suppressed sighting costs none; the probe is a function the caller supplies and must go through the same bounded navigation seam a walk pays into.
**The nightly ceiling is per agent, which is the opposite choice from `NavigationPolicy`'s and made for the opposite reason.**
A path search is a cost to the *server*, so agents must share one budget or the tick suffers; a model call is a cost to the *run*, and an agent that has spent nothing tonight has done nothing to deserve a refusal because its neighbour was busy being hunted - which under one shared ceiling is exactly the agent that dies unasked.
The consequence is deliberate: `MAX_PIVOTAL_THREAT_CALLS_PER_NIGHT` (8) is multiplied by the head count, not by the server, when an operator sizes a run's inference bill.
Reaching it suppresses the sighting rather than downgrading it to a cheaper tier, because a pivotal moment answered by a routine model reads in the record as a decision the agent made when what happened is that Loom stopped paying.
Reset is a day *boundary* from the world's own `dayOrdinal`, never an elapsed interval, so an agent that met its first zombie at dusk gets the same allowance as one that met its first at midnight, and `ThreatWatch.forget` drops the scene an agent stood in but never its spend - a body put away and spawned again must not come back with a fresh allowance.
`ThreatWatch`'s pivotal conjunction (`visible && insidePivotal`) is deliberately the same one `dev.loom.mind`'s `importanceOf` prices, and both leave `reachable` out: the engine refuses a route whenever the body is off the ground, and a body being hit is off the ground, so pricing on reachability would charge the cheap tier in the worst danger an agent will ever be in.
Every refusal is one append-only `threatSuppressed` record carrying `THREAT_DEBOUNCED`, `THREAT_UNCHANGED` or `THREAT_OVER_NIGHTLY_CAP`, because a run whose agent did nothing about an approaching zombie has to be able to say which bound never asked its mind.
It is deliberately **quiet on `/loomwatch`**: the append-only record is the evidence, and a note recorded once a second would fill all eight lines of a bounded display with the thing that did *not* happen.

**The vigilance loop is a coordinator above both ports, like `AutonomousDriver` and for the same reason.**
`BodyPort.senseThreat` is one call rather than "are there threats?" followed by `perceive`, because a ref means something only inside the request that minted it - a trigger from one capture sent with a second capture's perception names a handle the mind cannot resolve, and every flight it prompts is refused as a threat that was never named.
`ThreatDriver.sweep` therefore submits the port's own perception unchanged, classifying it on the way past, and does not decide what matters, read the world, or journal.
`THREAT_SCAN_CADENCE` (1 s) bounds *suppression records*, not model spend, which the debounce already bounds; scanning every tick would write twenty refusals a second for as long as anything hostile stood in view.
Only `liveBodies()` is scanned, so no dead or put-away agent is ever looked at.
This is what makes the shipped stand-in enough to watch a whole flight in world: `ScriptedBackend` answers a `threatSighted` trigger with `flee` naming the ref the trigger carries, so a hostile put in view of a body drives sighting, decision and retreat with no provider and no stand-in of your own - see the verification section below for the difficulty setting that otherwise removes the hostile before it is seen.

**The world clock is derived from the level's own time, and its countdown never reads zero.**
`SelfState.world` carries `dayPhase`, `isDay` and `ticksUntilNightfall`; `WorldClock` (engine-free) owns what the number means and `level.isDay` answers daylight directly, because a dimension with a fixed time has a day time and no daylight and the agent needs the difference.
`ticksUntilNightfall` counts to the *next* nightfall and wraps, so during the night it is a whole day rather than zero: zero for the length of a night would read as a nightfall permanently about to happen, and the phase is what says the night is already here.
The contract refuses a value below 1 on both sides *at decode* - `WorldState`'s `init` on the JVM, `positive_nightfall_countdown` in Rust - so that wrap is a type rule and not a convention.
Both are needed because nothing on either wire is schema-validated at runtime: `minimum: 1` in the schema is a rule a socket walks straight past, and for a while the Rust side deserialized a bare `i64` while this file claimed otherwise.
Only decoding is narrowed on the Rust side; serialization is left as the derive wrote it, so the fixtures still round-trip byte-for-byte.
**An entity ref's length is narrowed the same way, and for the same reason.**
The schema's `minLength: 1` / `maxLength: 8` is likewise a rule a socket walks past, so both `Observation.ref` and `Intent.Flee.from` refuse a blank or over-long handle at decode - `requireBoundedRef` on the JVM, `bounded_optional_ref` and `bounded_ref` in Rust, each runtime stating the bound once rather than at every field that carries a ref.
Both ends are worth refusing rather than merely odd: a blank ref names nothing the body can resolve, and refusing it keeps "a ref is present" and "a ref means something" the same statement, while an over-long one is a handle no request ever issued and so is a mind having invented one rather than named back what it was given.
Length is counted in **code points** on both sides, because that is what the schema's `maxLength` counts: Rust uses `chars().count()` and the JVM must use `codePointCount` rather than `String.length`, which is UTF-16 code units and measures a non-BMP handle double - one runtime accepting a ref the other refuses is exactly the drift stating the bound once per runtime is meant to rule out.
`contract/fixtures/invalid/decision-flee-blank-ref.json` and `perception-observation-ref-too-long.json` are pinned against the schema *and* against both decoders.
**An inventory stack's count is narrowed at decode on both sides too, and that field is the one where only one runtime ever reads.**
A `Perception` is written by the JVM and read by the mind, so the schema's `minimum: 1` and `InventoryStack`'s own `init` never see the line that arrives off the socket: `occupied_stack_count` in Rust is the check that would actually have caught it.
Zero is the value worth refusing rather than an odd one - `prompt.rs`'s `inventory_line` renders it as `0 bread (ref i1)`, which tells a model it is carrying food it does not have on the one path whose whole purpose is deciding whether to eat - and the body cannot have meant it, since an empty slot is omitted from the summary instead.
`contract/fixtures/invalid/perception-inventory-empty-stack.json` is pinned against the schema and against the Rust decoder.
**The summary's own length is a contract rule and is narrowed the same way**, unlike `surroundings`, whose length is the body's own policy and deliberately carries no `maxItems`: a ninth slot is not a body having chosen to say more but a body that read something which is not its inventory, and every handle past the eighth names a slot no eat could resolve.
`MAX_INVENTORY_STACKS` states it once per runtime - `SelfState`'s `init` on the JVM, `bounded_inventory_summary` in Rust - and `perception-inventory-over-slot-count.json` is pinned against the schema and both decoders, each also proving a full eight-slot body still decodes.
Note the two eights are stated in different packages: `BODY_INVENTORY_SLOTS` is how many slots a villager body has and `MAX_INVENTORY_STACKS` is how many the wire will carry, and `InventoryRefsTest.aBodyWithEverySlotFullStillFitsTheWire` is what keeps a flavor from outgrowing the wire silently.

**Death is terminal - Loom is permadeath.** When a body dies the agent is gone for good: no respawn, no reincarnation, no second body ever.
New agents will come from reproduction, never from restarting a dead one.
`NmsEntityBodyPort.tick` retires a body that has left the world - it drops from `bodies` - and then asks *why* it left before charging anything to the agent.
Only a departure that ends the agent reaches `Mortality`; then the death is recorded and `spawn` refuses that agent id from then on.
An agent can also end without anything happening to its body, by spending its energy reserve, so `NmsEntityBodyPort.die` is the single funnel both causes go through: "died once" must not depend on which cause reached the record first.
The rule is held by `Mortality` in the engine-free domain, which records a death and deliberately offers no way to clear one, so a revive path cannot be added by accident.
`BodyDeparture` (also engine-free) is the verdict on what a removal was, and `DEATH` is the only variant with `endsTheAgent`.
Despawning is not death: it is how Loom puts a body away (as on plugin unload) and leaves the agent embodiable.
A death owes the mind a *terminal* body-death `Trigger` once cognition is wired - "this agent has DIED", not "take another body".
That signal is deliberately not sent from `tick`, and no death `Trigger` exists in the contract yet, so it is left as a marked owed signal at the retire site rather than built now.
`Mortality` holds the dead in memory, so for a Villager body its refusal spans the server process, and making *that* death outlive a restart belongs with agent-identity persistence, which does not exist yet.
A *player* body's death is already durable, because a player account outlives the server and can reconnect where a Villager cannot: `DurablePermadeath` wraps this same rule with a tombstone ledger, and the player-witness section below owns how.
The append-only event log is meanwhile the durable record of who has died.

**The first survival drive is an energy reserve, and running it out is a death.**
`Metabolism` (engine-free) holds the reserve, spends it from the tick the port is given, and reports it - nothing more: ending the agent that ran out is the port's job through `die`, and whether an agent has ended stays `Mortality`'s to say, so death keeps one source of truth.
The reserve is counted in **ticks**, never in wall-clock time and never as the fraction the mind sees: the same tick sequence has to end the same agent at the same tick however fast it is replayed, a paused server must starve nobody, and a fraction decremented every tick would accumulate float error across a boundary that is a permadeath.
The unused adapter projects that 0.0-1.0 reserve onto `SelfState.food`'s 0..20 scale with zero saturation so its tests and implementation remain source-compatible with the player-shaped contract until removal.
The one knob is `DEFAULT_ENERGY_LIFESPAN_TICKS` (36 000 ticks, half an hour at twenty a second), a `Metabolism` constructor default rather than a config file: long enough that a body spawned to be looked at is not dying while it is looked at, short enough that a whole life fits in one sitting.
**Food is the only source of recovery, and `Intent.Rest` deliberately buys nothing.**
`Metabolism.feed` is the one way a reserve goes back up: it adds whole ticks, never past the capacity, and refuses a spent reserve.
Resting stops the body and holds its position on purpose, and that is the whole of it - a resting agent is spending its life waiting rather than buying any of it back, which is what makes food worth walking to and a night worth surviving.
`Rest` stays its own intent rather than a synonym for `Idle` because sealing a hole and waiting for dawn is a choice a survival run has to count separately from having decided nothing, and that distinction is kept in the outcome, the record, the prompt and the watch line.
What a food is worth is the engine's own number rather than a table of Loom's: `VANILLA_FOOD_BAR_NUTRITION` (20) points fill a whole reserve, so `ticksPerNutrition` is the capacity divided by twenty - integer division throughout, because no float may touch a boundary that is a permadeath - and bread at `FoodProperties.nutrition` 5 is a quarter of a life.
Deliberately not `Villager.FOOD_POINTS`, which encodes villager *breeding* semantics and disagrees with the engine's own nutrition (bread is 4 there and 5 in `FoodProperties`).
Feeding is carried out by the *port*, not the entity, because a dimension transit replaces a body and must not replace the reserve.
Exhaustion is terminal in the type and not only in the record - `Metabolism.feed` refuses a spent reserve, so an agent cannot eat its way back out of a permadeath.
The reserve is charged at the top of `NmsEntityBodyPort.tick`, so a body whose reserve has just run out takes no further step, and the deaths it causes are applied at the *end* of the tick, once every body is where the tick leaves it: an agent starving mid-transit is re-embodied on the far side first and dies there, rather than leaving the engine's leftover villager standing in the destination.
The reserve is in memory only, like the Villager body's `Mortality`; making either outlive a restart belongs with agent-identity persistence, which does not exist yet.

**A meal names one exact stack rather than a food, and `Eating.kt` is the whole rule for what may refuse it.**
`Intent.Eat` carries a handle the perception minted for one slot of the body's own eight-slot native container, so two stacks of bread are two different meals - one of them may be the last food the agent has.
`InventoryRefs` is deliberately a separate store from `EntityRefs` rather than a generalisation of it, because a creature handle names something whose identity outlives the request while a slot handle names a **position** whose contents change: the apply path must therefore re-read the slot and re-check that what stands in it is still food, which is a rule about eating and not about handles.
The verdict is the engine-free `mealFor`, and the order in it is load-bearing rather than tidy - the handle first, because an unresolvable one names no slot to look in; then the slot, so a stack eaten in between reads as an empty slot and not as a full reserve; then the reserve, so an agent that cannot use a meal still finds out what it was going to eat.
Every one of the six refusals is settled *before* the engine consumes anything, which is what keeps a refusal from costing an agent its food, and each has its own `EventTag` (`eatSlotForgotten`, `eatSlotUnnamed`, `eatSlotEmpty`, `eatNotFood`, `eatReserveFull`, `eatReserveSpent`): read as one uncountable `rejected`, a run could not tell an agent that had nothing edible from one that ate to a standstill and wasted the rest.
That is what `IntentOutcome.Rejected.tag` exists for - the reason is a *field* rather than prose, travelling in the ordinary `intentApplied` record's `outcome` the way `spawnRejected` carries its three - and a refusal with nothing more specific to say keeps the generic tag, so no record that already existed changed shape.
`BodyEating.kt` is only what needs a world: `DataComponents.FOOD` is the sole authority on what counts as food, so a food added or repriced by a version bump is priced correctly with no change here, and the engine's own `LivingEntity.eat` does the eating - sound, particles, effects, the game event, and exactly one item consumed by the rule that owns items rather than by arithmetic of Loom's.
`EnergyReserve.credit` then reports the ticks the agent **actually gained** rather than what the food was worth, because feeding stops at the capacity and a survival curve is drawn from those numbers.
**An item is named by the engine's own `descriptionId` and never by `hoverName`**, in the perception and in the record alike, which is the same vocabulary `Observation.what` already carries (`item.minecraft.bread` beside `entity.minecraft.zombie`).
`hoverName` is the *display* name: localized, and whatever an anvil or a datapack last called the stack - so a renamed loaf reached the model as its custom name on the one path whose purpose is deciding whether to eat, and the accepted-meal detail, which is the only place the record says what was eaten, counted display strings rather than items.
Eating is instantaneous in this version - no use time, no animation, nothing an agent can be caught halfway through - and the record says so by stating a completed meal.
`EatingTest` proves all six refusals and the arithmetic at a desk; the one thing no unit test can reach is that exactly one item leaves the stack, since that is the engine's own rule, so it belongs to the in-world proof.

**An agent has two vitals, and how each reaches the log is `BodyVitals.kt`'s whole job.**
The reserve above is one; the body's health is the other, and a body can be beaten to death on a full reserve, so a run that could not tell the two apart could not say what ended an agent.
`VitalsWatch` therefore gives each vital **its own `EnergyWatch`**, because they move for unrelated reasons: the reserve drains on a half-hour ramp while health drops in one hit.
A shared step function let a wound sit unrecorded until the reserve next stepped - up to eighteen seconds in world, by which time the in-world run that found it had a dead agent.
Each vital has its own event (`energyChanged`, `healthChanged`) and every such record carries **both** readings: which one moved is the event's name, and what the other stood at is what makes the record readable alone.
Records that carry a reading anyway (a spawn, a perception) tell the watch through `noted` so the next tick does not restate it; a record with *no* health reading passes none, since taking an unstated reading as recorded is how a wound would be silently dropped.
**No vitals record may follow a death.**
Only the actuate branch of `NmsEntityBodyPort.tick` samples them, for the same reason a movement record after a death is a lie: the other branches have no body of that agent's left to read, and an in-world run wrote two readings *after* the `died` record off an entity the engine had already removed.
Nothing is lost by it - a `died` or `despawned` record states the readings it ended on, and a traveller states its own from the spawn of the body it arrives in.

**Losing a body is not always losing the agent.** Loom is multi-dimension: an agent may walk into a nether or end portal, and that transit is continuity, not death.
So a removal has to be explained before it is charged to the agent, which is what `BodyDeparture` and `dev.loom.body.nms.departureOf` are for.
Read `BodyTransit.kt` before touching that classification; it records what the engine actually does at each seam.
Two of those seams are counter-intuitive:

- A dimension transit does not carry the body across. The engine builds a *plain vanilla* entity in the destination, copies state onto it, and removes the original with `CHANGED_DIMENSION`; the successor cannot be turned into a `LoomBodyEntity`, so Loom reads its arrival position, discards it, and re-places its own body there through the ordinary spawn path - which is also what takes the destination hold before the body counts as live.
  Loom's replacement body therefore inherits nothing automatically, and the portal cooldown has to be carried across by hand (`carryPortalCooldown`): the body arrives *inside* the destination portal, so without it the agent travels back and forth once per tick. An in-world run caught exactly that, 1465 times in under a minute.
- A conversion cannot be recognised after the fact: lightning turning a villager into a witch discards the original with `DISCARDED`, the same reason an ordinary discard uses. The only uniform seam is the cancellable Bukkit `EntityTransformEvent` (`BodyConversions`), which Loom cancels - a witch is not a body Loom can drive or perceive through - and records on the agent's own chain.

Both are logged as `travelled` / `converted` on the travelling agent's chain, never as a death followed by a birth, so the research record keeps one continuous life per agent.
A `converted` record says in its `outcome` which of the two conversions it was - `conversionRefused` for the body Loom kept, `bodyTaken` for the failsafe branch where the conversion took it and the agent is left unembodied - because those are opposite facts about whether the agent still has a body and nothing but the tag distinguishes them.

**Agents carry their own loaded world, and permadeath detection depends on it.**
Loom has no human players, so by default nothing keeps a chunk loaded and an agent nobody is watching stops ticking.
That is not merely a liveness problem: `RemovalReason.UNLOADED_TO_CHUNK` removes a body without killing it, so a bare "removed means dead" check would mark an unwatched agent permanently dead - an agent dying for want of an observer.
Instead Loom holds the world open around every living agent, in *every* dimension it has agents in, so an unload is never among the removals the port has to explain.
That is what lets `departureOf` treat an unexplained removal as a real death, and it has to hold in every dimension an agent can reach or the rule stops being sound there.
The policy is `WorldFootprint` in the engine-free domain, keyed by world, so nether and end holds are ordinary entries rather than a special case and a body that walks through a portal simply moves its hold (the coalesced union of a chunk area around each living agent, so cost tracks the population's spatial footprint rather than its head count, and a group that splits off keeps its own area); `dev.loom.body.nms.HeldChunks` is the engine half that makes the holds real and records each change to the event log under the reserved world-level agent id `loom:world`, which `AgentId` refuses so no agent's records can be mistaken for the world's.
The hold is taken before a body registers as live - spawn refuses rather than leave a live body unheld - and `follow` keeps it sliding with the agents from then on.
The mechanism is Bukkit's plugin chunk ticket, which lands at chunk level 31 - `ChunkLevel.ENTITY_TICKING_LEVEL` - so a held chunk ticks its entities.
That level *is* the invariant: hold chunks any more weakly and false deaths come back silently.
The *radius* now serves two further invariants - a path search reads unloaded chunks as air, and an entity query reads them as empty - so it is derived from the follow range and the perception radius rather than chosen here, and narrowing it costs correct routes and honest perceptions as well as correct deaths. See `holdRadiusChunksFor` above.
Tickets outlive the tick that added them, so they must be released on disable or the world stays pinned loaded with no Loom running.

**A hold failure must never be silent, and `follow` cannot refuse.**
Spawn can turn a bad hold down; `follow` cannot, because the bodies are already live and already there, so a hold failure during `follow` *is* the invariant broken rather than a request to decline.
Every attempt therefore returns a `ChunkHoldOutcome` (engine-free domain) rather than a count or a boolean, and an incomplete one is recorded as its own `worldHoldFailed` event *and* raised on the plugin logger ("world hold failed: ..."), naming the agents standing in an unheld chunk.
Before trusting any run's permadeath numbers, check the event log for `worldHoldFailed` - its presence means some removals classified as deaths may have been unloads.
The two ways a hold can fail are kept distinct (`unknownWorld` versus `ticketDeclined`): one is a Loom-side mistake, the other the engine declining a correct request, and an earlier version collapsed both into a bare `false` that made every failure invisible.
Note that Bukkit also returns false for a ticket already held, which is why only chunks outside the held set are ever asked for.

## The player witness

`dev.loom.witness` is the server-authoritative witness for Loom's *player* bodies - the Mineflayer flavor of `body/` - and it is a second, independent permadeath enforcement point rather than a helper for the Villager one.
It is active before any body can launch: `LoomPlugin.witnessPlayers` replays the ledger and installs the listener, then `PlayerBodyPort.spawn` registers the deterministic username/UUID before starting the child.
`dev.loom.witness` is engine-free by rule and `dev.loom.witness.bukkit` is its one adapter, both pinned by `WitnessBoundaryTest`.

**Paper is the witness because Node cannot be one.**
A Mineflayer client reports what it was told; the server knows what happened, and a client that has crashed or been tampered with reports nothing at all.
So the plugin listens to `AsyncPlayerPreLoginEvent`, `PlayerJoinEvent`, `PlayerQuitEvent`, `PlayerDeathEvent` and `PlayerRespawnEvent`, and Mineflayer's `respawn: false` plus vanilla playerdata stay *independent* protections rather than the mechanism - three things must fail before a dead agent walks again.

**Death is terminal across restarts, which `Mortality` alone cannot give a player body.**
A Villager exists only inside a running Loom, so an in-memory death set is enough for it; a player *account* outlives the server and can reconnect, so a death held only in memory is a death a restart undoes.
`DurablePermadeath` therefore wraps `Mortality` with a `DeathLedger`, and the two files Loom writes are not the same kind of thing.
`plugins/Loom/body-events.jsonl` is **evidence**: asynchronous, bounded queue, may drop records, and cheap to lose a moment of.
`plugins/Loom/player-deaths.jsonl` is an **authorisation input**: one tombstone per line, written synchronously with `StandardOpenOption.SYNC` before the death is reported as final, and read exactly once.
Being synchronous costs one file sync per agent lifetime, which is why it is affordable at all.

**The replay ordering is a constructor, not a call to remember.**
`DurablePermadeath`'s `init` reads the ledger, so the object cannot exist in a state that has not caught up with previous runs - that *is* the requirement that tombstones replay before login admission begins, and `LoomPlugin.witnessPlayers` constructs it before registering the listener.

**The ledger is authoritative for admission, and the replay therefore keeps the whole identity rather than the agent id.**
An agent id can only be compared against a registration, and a registration lives in the memory of one process: the body driving a dead agent's account is started by something Loom does not own, so it can reconnect before - or without - anything registering the identity again, at which point an agent-id-keyed answer has nothing to compare and the dead walk in unrecorded, after exactly the restart the ledger is written synchronously to survive.
So `DurablePermadeath.deadIdentityFor` answers from the uuid and the username the tombstone itself carries, `PlayerWitness.admitLogin` asks it *first* - before the registry and before the seal - and the `witnessDenied` record is filed under the agent id the tombstone names.
Either half is enough, because a tombstoned uuid connecting under a new username and a tombstoned username connecting from a new account are both a dead agent's account trying to get back in.
`admitKnown` still asks `isDead` afterwards, and that is not the same question: it is keyed on the agent behind the registration, which is what catches an agent re-registered against a different account after it died.
A tombstone Loom cannot read back *at all* seals rather than being passed over, since skipping it would reopen the gap for that one agent, and a throw would leave the server with no witness at all - but the two halves of a tombstone fail independently and `remember` takes whichever it can.
A mangled uuid still leaves the agent id and the username perfectly legible, so `remember` takes each field that reads on its own: the agent id records the death, and whichever of the uuid and the username re-validates is indexed so a connection presenting it is still refused.
Discarding the whole line made `isDead` answer false for an agent the file names, and the login was then refused as a ledger Loom could not read rather than as the death it plainly is; indexing neither half was worse, because the seal cannot stand in for an index - it is consulted only for a connection a *registration* has already matched, so after a restart it refuses nobody, and a hand-edited uuid was enough to re-admit an agent whose death the file still stated by name.
That is what `DeadMatch` distinguishes: a tombstone that read back whole hands back the identity it named, and one that did not hands back the agent id alone, so a refusal from it states the connection and never a uuid no file ever held.
The death index and `WitnessRegistry.byUsername` read a username the same way, both through `usernameKeyOf`, which lowercases with `Locale.ROOT` because the default locale would make a lookup depend on the operator's machine.
`BodyEventRecord.witness` means one thing on every witness record, including a refusal: the connection the server actually saw.
A tombstone is matched on *either* half, so filling those fields from the tombstone instead named a player that never presented itself - a username nobody offered, or a dead agent's uuid for a connection from another account entirely - and those two fields are the join to a server log line and to a `playerdata` file, so a record naming a player that never connected lands that join on the wrong row.
The tombstone's own identity is kept in the `detail` beside the connection, which is what shows an operator that only one half of the recorded identity matched; a refusal filed under the tombstone's agent with neither stated would read as that agent's own account trying to get back in.
That is the rule on the *ordinary* records too - a join, a quit, a death, a revival - which is why `sawJoin`, `sawQuit`, `sawDeath` and `sawRespawn` all take the username beside the uuid and `subjectOf(agentId, uuid, username)` is the only way the witness builds a subject.
It diverges there without any breach at all: after a login the lookup is by uuid alone, so an account renamed against a stale registration was recorded under a name nobody offered, and a `Matched` login agrees on both halves only up to case.
The two halves answer different questions and are never interchangeable - the agent is Loom's own resolution and the player is the server's report - which is also why a death writes its *tombstone* from the registration: that file is an authorisation input matched against every later login, not evidence of one connection.

**An unreadable ledger is unsafe, never empty, and sealing and enforcing are not alternatives.**
A *missing* file means nobody has died yet, which is the ordinary state of a fresh run and the one absence safe to read as "no deaths".
A file that exists and will not parse - including a torn final line from a crash mid-append - means Loom does not know who is dead, which is not the same as knowing nobody is, so it seals the witness one-way and refuses every *managed* login until a human looks.
The run loses availability for its player bodies and keeps the invariant, which is the right way round here.
**Every death the replay could read is still enforced, and the seal covers only the line it could not.**
`LedgerReplay` carries its tombstones on *both* variants for that reason: a crash mid-append tears the last line only, and the whole synced lines before it state their deaths perfectly well, so `FileDeathLedger` accumulates up to the first line it cannot read and stops there rather than throwing the lot away.
Reading the two as alternatives was a real hole, because the seal alone refuses only the identities a *registration* names, and after the restart it exists to survive there are none - so a torn final line let every earlier death's account walk back in unrecorded.
Fail-closed never reaches a stranger, torn ledger or not: the seal is only reached for a connection the ledger or the registry has already identified as Loom's, so an unrelated player is admitted and nothing is recorded about it, not even a refusal.
Sealing does not throw, because a plugin that failed to enable would leave the server with no witness at all - failing closed only works if the thing that failed is still there to refuse.
A seal states *every* fault it found, since a partly readable tombstone and a torn final line can be in one file at once and each is a different thing to go and look at, and each fault names its own unit (`tombstone 2` counts tombstones, `line 3` counts file lines, and the two diverge as soon as a blank line is present).
The `loginLedgerUnsafe` record's `detail` is the seal and nothing else, because that detail is capped at `MAX_WITNESS_DETAIL_CHARS` (192) and prefixing it with the notice the *client* is told spent 114 of those on a sentence the record's own tag already carries - which cut the second fault out of the one place an operator reads the faults back after the fact.
For the same budget a fault states only what went wrong, identifier first, and leaves the consequence to the alert and the notice that each state it once.
That budget is the record's alone, and `sealReasonWithin` is where it is spent: the operator alert reads `sealReason`, which is bounded only by how many faults are worth naming, because a server log line has no width to run out of and it is the one place a fault the record had to elide can still be recovered from.
One string for both readers made the tightest bound everybody's, so the log named fewer faults than it could and dropped exactly the ones the record had.

**A login is resolved against the ledger first, then by uuid *and* username; everything after it by uuid alone.**
A tombstoned identity is a managed identity by definition, so consulting the ledger first does not widen what Loom has an opinion about: a connection matching neither a tombstone nor a registration is still `Unmanaged`, still admitted, and still recorded nowhere at all, which `PlayerWitnessTest` covers with tombstones sitting in the ledger.
Login is otherwise the one moment something can claim to be a managed body without being one, so a connection matching half a registration is `Mismatched` and refused rather than resolved.
After that the server's own uuid is authoritative - resolved against the registry and, for the two breach failsafes only, against the death ledger as well - and there is deliberately no *username* fallback anywhere after the login, which is what makes "an unrelated player is never recorded" a property of the lookup rather than of a check somebody must remember to write.
`breachSubject` is that whole rule and sits beside `claimOf`, taking its two sources explicitly for the same reason.
The ledger half of it is what makes a breach visible in the run the ledger is synchronous for: reaching `sawJoin` or `sawRespawn` with a dead agent means the login refusal did not hold, and after a restart nothing is registered - so a registry-only lookup left exactly that breach with no record, no alert and no removal.
`sawQuit` and `sawDeath` stay registry-only, because a quit or a death of an unregistered player is not a breach and recording one would witness a player Loom was never asked about.

**Exactly one death record per agent is decided in one place.**
`DurablePermadeath.recordDeath` takes the in-memory claim and writes the tombstone under one lock, and answers `Terminal` / `AlreadyRecorded` / `Unpersisted`; only `Terminal` writes a `died` record.
The lock is not an optimisation: a login refusal runs on a Netty thread during async pre-login while a death is witnessed on the main thread, and `Mortality` holds a plain `HashSet`.
`Unpersisted` still records the death and still seals, because the agent is dead either way and what was lost is only that it stays dead.

**A quit after a recorded death records nothing.**
That is what keeps a terminal death the last thing in an agent's chain apart from bounded `witnessDenied` records: the death asks for a removal, and Bukkit reports that removal as an ordinary quit.
An ordinary quit *before* a death is continuity and writes no tombstone.

**`PlayerRespawnEvent` is not the after-a-death event its name suggests, and reading it as one is an irreversible false permadeath.**
`RespawnReason` has three values, and only `DEATH` reports a death: `END_PORTAL` fires for a perfectly *live* player stepping into the End's exit portal, because vanilla sends that player to its respawn position rather than through an ordinary portal (`EndPortalBlock.getPortalDestination` calls `findRespawnPositionAndUseSpawnBlock(..., RespawnReason.END_PORTAL)`), and `PLUGIN` fires for anything that respawns a player itself.
Handed to the witness undifferentiated, an agent walking home from the End was recorded dead, tombstoned synchronously and kicked for good, with nothing in any log to contradict it.
So `dev.loom.witness.bukkit`'s `respawnCauseOf` translates the reason into `RespawnCause` and does nothing else, total over the enum so a reason a version bump adds cannot default into being read as a death; a dimension return is continuity for a living agent, exactly as `BodyTransit.kt` already treats it for the Villager body.
The in-world proof drove deaths only with the console `kill`, which is why it could not have caught this - a run that means to prove the respawn path has to walk a body through the End's exit portal.

**The reason alone is not the rule, though, which is why the decision is the witness's and not the adapter's.**
A respawn the server reports as following a death is always a breach and always witnessed.
A respawn with no death behind it is a breach only when the agent is *already* tombstoned - something on the server has put a dead agent back in the world, and the run has to say so - and is nothing at all for a living agent, which is what keeps a body walking home from the End free of a `died` record, a tombstone, a `witnessRevived` record, an alert and a removal.
Both halves need the durable death state, which `dev.loom.witness.bukkit` deliberately cannot see; `RespawnCause` carries the server's meaning across that seam without the Bukkit enum crossing it.

**`witnessRevived` is the impossible case, and it exists to make an incorrect run visible.**
A `PlayerRespawnEvent` cannot be cancelled, so by the time one fires for a breach the world already holds a live player for a dead agent; the same is true of a join the pre-login refusal did not stop.
Every one of them records a revival, alerts the operator, and asks for the removal, and the two respawn paths are indistinguishable in kind - the same event, the same `revivedAfterRespawn` tag - because anything counting breaches reads those rather than the prose.
A respawn *from a death* records the death first, because it is itself a report that the player died and the ordinary death path may be what failed; a respawn with no death behind it records none, since the agent it is about is already in the log with exactly one.
Neither failsafe needs a registration to fire, and a breach reached without one records neither a second death nor a second tombstone: the tombstone the ledger already holds *is* the death, and `recordDeath` would answer `AlreadyRecorded` for it anyway.
Such a revival is filed under the agent id the tombstone names, with the presented uuid and username in its `witness` fields, so a breach reads the same whether or not a registration happened to exist.
It reads as a contradiction of "no records after a terminal death" and is not one: a `witnessRevived` record means the invariant was already broken before Loom could say anything.
On the display it is read as the permadeath it proves - `DEAD`, final, with the reserve frozen - because every path that writes one has already established the death, so the record needs no `died` record beside it to be believed; that is what a watch attached *after* the fact gets, exactly as `loginDeadIdentity` already gives it.
The live player the world is holding is the breach rather than a body, and the `ALARM` note is what says so: a state that called it a body would have to call the agent alive, which is the one thing a permadeath display may not do.

The witness owns no removal mechanism.
It answers `WitnessAction.Remove` and the adapter kicks on the next tick, which is what lets exactly-once death be proved at a desk with no server to be kicked from.

**The same asymmetry applies to a body's readings, and the cross-check that does it is deliberately not part of the witness.**
A `sense` answer's vitals and inventory are what a *client* was told, so the numbers a survival run measures are only worth what the server will vouch for.
`ClaimAudit` compares one against `dev.loom.witness.bukkit`'s `PlayerReading`, and it is a separate object from `PlayerWitness` rather than a method on it because the witness decides two irreversible things and a cross-check decides none: keeping them apart in the type means widening what is cross-checked can never reach the permadeath rule.
`Corroboration.kt`'s own header is the authority on the three comparison rules - a bounded claim against an unbounded server reading, a tolerance for a continuous vital against exactness for an item, and coverage in both directions - so they are not restated here.
The one fact that lives nowhere else is that `dev.loom.witness` now depends on `dev.loom.bodycontrol` for the claim types, one way only, and `BodyControlBoundaryTest` pins that direction.
`InventorySlots.kt` owns the arithmetic between Bukkit's `PlayerInventory` numbering and the protocol's 46-slot window, and it is its own file because a mistake in it reports every armour piece in the wrong slot, which reads as a body that lied rather than as arithmetic.
Bukkit cannot address the five crafting-window slots at all, so a claim about one is counted and stated as outside the comparison: "the witness did not look" must never read as "the witness agreed".
A disagreement is one `witnessDisputed` record under one of six countable tags, and agreement is recorded nowhere and has no method - a record per cross-check that found nothing would bury the ones that did.
`BukkitPlayerServerState` submits every accepted sense and movement report. A dispute remains evidence only; it never changes admission, lifecycle or mortality.

**A movement report is cross-checked the same way, by the same object, and the three tags it can be filed under are the other three.**
`ClaimAudit.sawMovement` compares a `MovementClaim` - what one paired `moveTo` or `flee` request and report said - against `PlayerReading`'s `ServerStanding` through `corroborateMovement`, obeying every rule `sawClaim` does: resolved by uuid alone, a stranger is `NotManaged` and is recorded nowhere, and only a dispute is journalled.
The pairing requires both `requestId` and `agentId`, carries that agent into the claim, and refuses an audit whose registry identity differs before any witness evidence can be filed under the wrong agent.
`MovementCorroboration.kt`'s own header is the authority on its four rules, and two of them are the ones a reader would not guess.
Two of its three faults need no server at all, since a route shorter than the straight line between its own two ends and an arrival too far from the destination the request named are the body's own report contradicting itself, so they are checked whatever the server has to say.
And separation is deliberately **not** cross-checked: a flight's separation is measured against a creature named by a `senseId` and an ordinal, which resolves inside the body process alone, so the server was never told which entity a flight ran from and cannot be asked whether the ground gained was real.
`DISPUTED_MOVEMENT`, `DISPUTED_POSITION` and `DISPUTED_JOURNEY` are the three tags, and `tagOf` picks between them by which kinds of fault the dispute holds rather than by prose.

The product itself now supplies the in-world proof. `/loombody create` registers and launches the identity, a child-process kill proves quit/disconnect continuity, vanilla `kill <username>` proves exactly one server-witnessed death, and a direct launch of that account after restart proves ledger-first `loginDeadIdentity` denial. `DEMO.md` is the complete sequence.

## The unused Villager adapter and NMS seam

`dev.loom.body.nms` remains the only package in the plugin allowed to touch `net.minecraft` or CraftBukkit, but `LoomPlugin` no longer names or constructs it. Keep it source-compatible and keep its boundary tests green until the dedicated removal change; do not add a runtime switch back to it.

Read the header of `dev/loom/body/nms/LoomBodyEntity.kt` before changing the body's mechanism.
It records why a literally-new registered entity type is not viable here, why the body extends a vanilla class instead, and why the base type is Villager.
It also records that a Loom body is **not** safe from attack, whatever "not a monster" suggests: the whole illager line and, unless `spigot.yml` says otherwise, zombies and drowned all target `AbstractVillager` on sight, so a run measuring starvation rather than predation has to choose those settings deliberately (`DEMO.md` lists them).
Five sharp edges are easy to reintroduce:

- Spawning must use `SpawnReason.CUSTOM`; any other reason routes through natural-spawn gating that silently discards the body.
- `Mob.serverAiStep` is `final`, so suppressing vanilla behavior means overriding **both** `Villager.customServerAiStep()` (deprecated) and `customServerAiStep(boolean)` without calling `super`. Missing one gives the body vanilla behavior back.
- The navigator is untouched by that suppression, and that is deliberate: `Mob.serverAiStep` ticks `navigation`, `moveControl` and `lookControl` *outside* the `customServerAiStep` hook and outside the every-other-tick branch that gates the selectors, which is exactly why a body with zero goals still walks a route Loom put on it.
- `FOLLOW_RANGE` MUST be set in the `createNavigation` override and that is the ONLY place it can be. `PathNavigation`'s constructor reads the attribute once to fix the path finder's node budget, and `Mob`'s constructor builds the navigator before any Kotlin `init` block or property initializer runs - so for the same reason that override may read no property of the class, only inlined `const val`s.
- Bodies must keep renewing their own activation (`LoomBodyEntity.readyForTheEngineTick`). Spigot's activation range only activates entities near a *player*, and Loom has no players, so an untouched body drops to `inactiveTick` after ten seconds. That does not just idle it: it silently stops the whole server-AI chain, so a body stops walking its route, and it silently disables portal travel, because the transit is driven from `Entity.postTick`, which an inactive entity never reaches - a body would stand in a lit portal forever with nothing in any log to say why.

There is no `setPos` and no `deltaMovement` write left anywhere in Loom, and there must not be one again: the navigator's `MoveControl` owns the body's position while a route runs, and a second writer would fight it.
Movement is therefore *observed* rather than caused - `observeDisplacement` reads where the engine left the body and `describeJourney` says what its route is doing there, which is how a body walking node three of nine, a body the engine gave up on as stuck, and a body merely falling stay distinguishable in the record.

Engine helpers specified in extents rather than radii have already caused one bug (a perception radius that covered half its documented area).
Prefer expressing such bounds in the domain, as `PerceptionBound` does, where a test can pin them.

**Adding a future flavor** (fake player, external client, headless sim) means: a new package under `dev.loom.body`, a new `BodyPort` implementation in it, and one changed construction line in `LoomPlugin`.
Nothing above the port should need editing; if it does, the port is leaking. The ArchUnit rules already require any new implementation to live in its own adapter package.

The plugin ships with the stable `plugin.yml` descriptor, not `paper-plugin.yml`: Paper's own descriptor drops declarative `commands:` in favor of Brigadier registration, which is still experimental API on 1.21.1 and cannot be opted into under warnings-as-errors.

## The mind, and the bridge to it

`cognition/crates/cognition` is the mind: it accepts a `Perception` and returns a routed, provenance-stamped `Decision`.
Five pieces, each its own module - `router` (tier to model), `model` (the backend seam), `openai` (the one real backend), `mind` (compose and stamp), `server`/`wire` (newline-delimited JSON over TCP).
`ScriptedBackend` is still the default, so a fresh checkout runs with no credentials and both suites stay hermetic, but it is the fallback rather than the state of the art: `LOOM_COGNITION_BACKEND=openai` selects real inference, and `cognition/README.md` is the operator documentation for every setting it reads.
It answers a goal review whose vanilla `food` is at or below `LOW_FOOD_LEVEL` (7) by naming the first stack the body reported and eating it, resting only when the body reported nothing to eat. That is deliberately a goal-review rule rather than an auto-eat reflex in Node.
That is deliberately a goal-review rule and not a reflex: a damaged agent still flees, because escaping the threat now outranks feeding itself.
A `damaged` trigger flees the nearest thing in sight carrying a `ref` rather than the trigger's `source`, since a flight names one creature and not a species, and it idles when nothing in sight can be named at all - a handle the body never issued would be refused, so an agent would have spent a pivotal decision on an action that could never be carried out.
A `threatSighted` trigger looks nothing up, because the handle for that one creature travels with the trigger: reading the surroundings there would answer a sighting of the thing behind the agent by fleeing the thing in front of it.
A misspelled backend name stops the service instead of falling back, because scripted decisions look real in the log until someone reads their provenance.
Every number a `reasoning` states is rounded where it is interpolated, because `reasoning` is the one field `ObserverView.showsDetail` carries verbatim to a boss bar: a reserve derived from a tick count printed as `down to 0.3198888888888889` in world, and a health that is an `f32` widens to `19.899999618530273`.
The exact values stay in the perception and in the record's own fields, where anything counting them looks.

**Provenance is stamped by `Mind::decide`, never by a backend.** `ModelRoute` has private fields whose only constructor is `route(importance)`, so a decision cannot claim a model it was not routed to; `mind.rs`'s `LyingBackend` test pins that.
Routing is total over `DecisionImportance` with no default branch - a new tier will not compile until its model is chosen, because a tier silently defaulting is how routine traffic reaches a frontier model.
The refusal frame `{"error":...}` is deliberately **not** a contract type: a mind that could not answer has not decided anything, and inventing an `Intent` for it would put a fiction in the decision record.

**No failure out of `openai` may carry the prompt or the credential, and that is the module's main design constraint rather than a habit.**
Four defences hold it, and each is easy to undo by being helpful: the credential exists only as an already-sensitive default header; the provider's error `message` is *not deserialized at all* (only its short `type`/`code` are repeated, bounded), so no code path can start logging it later; a malformed answer is reported as a `serde_json` category plus line and column, never as text, because a model answer can quote back the perception it was given; and `reqwest`'s own `Display` is used only for the residual transport case, via `root_cause`, where request data has never been.
`tests/openai_provider.rs` sweeps every provider failure path against a credential marker and a prompt marker at once, so a leak added later fails there.

**The answer's shape is enforced by a strict `json_schema`, and that schema is the one thing here that can silently fall behind the contract.**
It mirrors the contract's `Intent` union by hand, so a new variant would compile everywhere and simply never be chosen - the provider would refuse to emit an action the schema does not list.
`tests/openai_request_schema.rs` therefore pins it against `contract/fixtures/valid/decision-*.json` in both directions, and adding a contract case (which already means adding a fixture) fails it until the request schema follows.
Strict mode also forbids `minItems`/`maxItems`/`oneOf`, so `moveTo`'s three coordinates are enforced by the contract type instead and arrive as a bounded malformed-answer error.

Three more sharp edges in `openai`, none of them guessable from the code:

- **The timeout chain spans both runtimes**: `LOOM_OPENAI_TIMEOUT_MS` (12s) < the body's `readTimeout` (14.5s) < the body's bridge `timeout` (30s). The mind's bounded "the provider did not answer" only reaches an operator if the body is still waiting for it; `CognitionSettingsTest` pins the ordering from the JVM side, restating 12s because the two runtimes share a contract and not a configuration. Moving one means moving all three.
- **`max_completion_tokens`, and no `temperature`.** The current models refuse `max_tokens` outright and accept only the default temperature, and a request refused at the API is a decision an agent does not get. The token bound is deliberately loose because reasoning models spend hidden tokens from the same budget and running out arrives as a *truncated answer*, not an error.
- **Nothing in the mind retries** - see the at-most-once note below. `http` base URLs are allowed only on loopback, which is what makes the crate's own mock provider possible without ever letting a credential cross a network in the clear.

On the JVM side `dev.loom.mind` is the port and is engine-free by rule (`MindBoundaryTest`), with `dev.loom.mind.tcp` the one transport adapter.
Three properties are the whole point of `AsyncCognitionBridge` and each has a test that fails if it is lost: `submit` never runs cognition, every request has a deadline, and back pressure is an explicit `Saturated` failure rather than an unbounded queue.
Three subtleties are load-bearing:

- **The watchdog frees the caller, not the worker.** A thread parked in a socket read stays parked, so `CognitionSettings.readTimeout` is derived from the bridge deadline and is deliberately shorter. Configure them independently and a stalled mind quietly consumes every worker.
  The derivation budgets a *whole* `ask` - both connects and both reads of its one retry - not a single read, and `ATTEMPTS_PER_ASK` in `dev.loom.mind` is that one fact: the settings divide the bridge deadline by it and the transport multiplies its read timeout back up by it, so raising the transport's retry count means raising that constant and nothing else.
  That budget is spent as a **wall-clock deadline inside `TcpCognitionTransport`, not as a socket timeout**, because `soTimeout` bounds one read syscall rather than one line: `BufferedReader.readLine` loops until a newline and every arriving byte restarts the clock, so a mind dripping one byte per interval held a worker 40s inside a 2s read timeout.
  The transport therefore frames response lines itself - chunk-wise, scanning the bytes already in hand for the newline and carrying whatever followed it into the next response, the way the mind's own `read_frame` works - re-narrowing the socket timeout to what is left of the budget before every read that could block, and capping the accumulated line at the same 256 KiB `read_frame` caps requests at.
  What the deadline actually cuts short is the **read** side, across a whole `ask` including both reads of its one retry.
  It does not narrow the connect legs, which are charged to the budget but bounded by `connectTimeout`, and it does not reach the write leg at all: Java exposes no `SO_SNDTIMEO`, so the write is bounded by `PerceptionBound` keeping a perception small enough to fit a send buffer, not by the clock.
  Fitting both connects and both reads inside the bridge deadline is `CognitionSettings`' arithmetic, not the transport's.
  A drip test pins the clock half and a cap test the byte half, and the drip test needs its preemptive timeout: on regression the `ask` never returns at all, so a plain assertion would hang the suite instead of failing it.
- **The deadline is armed before the work is queued**, so queue time counts against it. A per-attempt timer would let a request behind a stalled worker wait indefinitely.
- **Delivery to the mind is at-most-once, and the write is the seam.** `TcpCognitionTransport` retries only a failure at or before the write, where nothing can have been decided; anything from the read onward is reported. Re-sending past the write would risk a second billed inference for one perception, and a lost decision is cheaper than a duplicated one. Widening the retry to cover the read is the easy mistake, so a test pins that a perception reaches the mind exactly once.

Importance is classified above the body port by `importanceOf` (`Importance.kt`), not by the body and not by the mind: the body reports what happened, and what that costs is this side's call.
`EmbodiedCognition` is the only place the two ports meet - perceive on the main thread, decide off it, apply back on it through the `MainThread` port.
`BodyPort.tick` still never invokes cognition; the contract has no per-tick `Trigger`, and `BodyBoundaryTest` forbids `dev.loom.body..` from depending on `dev.loom.mind..` at all, so the tick path cannot reach a mind even by accident.

**Agents drive themselves, on a schedule that is policy rather than plumbing.**
`AutonomousDriver` sweeps on its own Bukkit timer - never off the per-tick body timer - and asks `GoalReviewSchedule` whose turn it is; both are engine-free, so the cadence and the stagger are pinned by unit tests with a fake clock.
The one knob is `DEFAULT_GOAL_REVIEW_CADENCE_TICKS`, and the sweep period is *derived* as `GoalReviewSchedule.sliceTicks`: sweep at any other rate and the per-slice share silently stops meaning one review per agent per cadence.
Both the schedule reading and Bukkit timer are authoritative server ticks. A pause advances nothing and `/tick sprint` advances the same deterministic sequence; wall time must never re-enter this path.
A never-reviewed agent is due at once, which is what keeps a single-agent demo watchable at a conservative cadence.
The driver is cancelled explicitly in `onDisable`, before the bridge it feeds closes.

**A decision enters the research record from the applied path, and only from there.**
`EmbodiedCognition.actOn` is the one place that holds the decision, the mind's stamp on it, and what the body did about it at the same time, so `DecisionJournal` writes `decided` there - before `apply`, so a run reads perception -> decision -> action - and `decisionDiscarded` when the body has gone in between.
Provenance is *carried* from the `Decision`, never re-derived on this side, and the record is filed under Loom's own `AgentId` rather than the mind's echo of it.
`requestId` is on all three records because several agents can think in one tick, so the join is by id and not by tick; `BodyPort.apply` takes one for that reason alone and defaults it to `null` for an intent no perception asked for.
The invariant is one `intentApplied` *or* one `decisionDiscarded` per `decided`, which is why `NmsEntityBodyPort.apply` journals nothing on its `NoSuchBody` early return.
`LoomPlugin.reportApplied` is an operator convenience for watching a round trip on a console, not the record.

A decision reaching a body is proven three ways, in increasing fidelity: `EmbodiedCognitionTest` (fake mind, queue-draining `MainThread` that asserts which thread touched the body), `TcpCognitionTransportTest` (real socket, canonical fixture bytes as responses), and `LiveCognitionServiceTest` (the real Rust service).
The last is opt-in via `LOOM_COGNITION_ADDR=host:port` so the default suite stays hermetic - `cargo run --bin loom-cognition`, then run the plugin tests with that variable set.
CI's `bridge` job does exactly that and then greps the JUnit XML for `skipped="0"`, because a skipped opt-in test would otherwise make the job green while proving nothing.

The provider path is proven the same way, one layer further out: `tests/openai_provider.rs` drives the whole mind against a hand-rolled HTTP/1.1 mock on an ephemeral loopback port.
It is hand-rolled rather than a mocking crate because several of the failures worth pinning - a provider that never answers, one that sends more than Loom will read - are socket behavior, and a mock that is not a socket cannot express them.
**No test may reach the live provider, and no test file may contain a credential**; the mock asserts nothing itself, since a panic on its spawned task surfaces at the client as a dropped connection rather than as the assertion message.

## The observation path

`dev.loom.observe` is the operator display: one watcher, one agent, `/loomwatch`.
`DEMO.md` is its operator documentation, the way `cognition/README.md` is the mind's - the exact local procedure, the field guide to the standing line, and the honest caveats all live there rather than here.
The package is engine-free by rule (`ObserveBoundaryTest`) and its one adapter is `dev.loom.plugin.BukkitObserverSink`.

**It is read-only by construction, not by discipline.**
`Observatory` holds no `BodyPort`, no cognition bridge, and no world handle, and its only input is the `BodyEventRecord` stream that `ObservedEventLog` offers it *after* the real log has taken each record.
So the proof that watching cannot disturb a run is a statement about types, not about timing, and adding any of those three handles to reach "just one more field" is what would break it.
The sink is one-way and cannot be read from, which is what makes "operator-only diagnostics never become agent-facing perception" structural: nothing shown to an operator has anywhere to travel back to.

**The observer/evidence vocabulary is a compatibility contract.**
The player perception carries vanilla `food` and `saturation`, but the established event log and observer retain `BodyEventRecord.vitals`, `energyChanged` and the `energy` line label in this cutover. `PlayerBodyPort` projects food onto that 0..20 slot; health remains separate, and saturation remains in the perception/decision record. Do not rename or fork those observer fields while changing the body adapter.
The colour is the one thing that reads both primary survival vital and health, at the same threshold.
Inside either field a reading is `level` of `capacity` (`AgentVitals.energy` carries a `@SerialName`), because `AgentVitals` is the shape *both* vitals are reported in: a health reading read back out of `health.energy` would be the same aliasing one field further down.
Before the reserve existed the display used health *as* energy; that shortcut is what the wire test in `BodyEventLogTest` now pins against, with the two readings deliberately on different scales so feeding one from the other fails.
`resting` and `idle` are likewise separate activities now that `Intent.Rest` and `Intent.Idle` are separate intents, and telling a deliberate wait from an unconsidered one is most of what a survival run is about - neither restores anything, so what separates them is intent alone.

**What a record *means* is read from a field, never from its prose, and six events need a field to say it.**
The view reads `event` plus the countable tags, so an event whose name carries two opposite meanings is an event the display gets wrong.
The six are `spawnRejected`, `converted`, `retreating`, `intentApplied`, `witnessDenied` and `witnessDisputed`, which is the set the *note* has to read; `WatchState.kt`'s own header counts a different four, because `TaggedActivity.kt` answers the narrower question of which events change the *activity* and that set drops `retreating`, `intentApplied` and `witnessDisputed` while adding `cognitionUnavailable`.
Neither count is the other's, and both are stated where they are because the two questions are asked in different places.
`spawnRejected` is one, and it carries three different facts rather than two.
`alreadyEmbodied` is refused *because* the agent still has its body, where most refusals happen to an agent that has none, and reading them alike labelled a live, visible body `no body` for a whole goal-review cadence.
`hasDied` is the opposite extreme: it is the *terminal* state itself rather than a request that failed, so it reads as `DEAD - will not return` in alarm and says the permadeath in the same words the `died` record does.
Read as merely bodiless it understated a permadeath as a temporary condition, and it is the one refusal a watch can meet without ever seeing the death - a watch attached after the fact has no other record that will ever say the agent is gone.
`converted` is another such event: `conversionRefused` left the body untouched, while `bodyTaken` took it and nothing re-embodies the agent.
`retreating` is the third, and the one where the tag carries the whole of the meaning: a single event name covers a flight starting, carrying on, waiting, ending safely and being left standing in range of something hunting it, which is why `ObserverView.retreatNote` reads the tag and never the detail.
`intentApplied` is the fourth, and it is the one where a *set* rather than a single value is what the display has to read: since `IntentOutcome.Rejected` carries its own tag, `rejected` is only what a refusal with nothing more specific to say arrives as, so `ObserverView.appliedNote` tests `INTENT_REFUSAL_TAGS` (derived in `EventTag.kt` from `EAT_REFUSALS`, so a refusal added there is covered the day it is added).
Testing for `rejected` alone made every eat refusal read as `the body did not act on it` - the sentence reserved for a decision that reached no body at all - so an operator could not tell an agent that was already full from one whose decision never arrived anywhere.
`witnessDenied` is the fifth, and its three `LOGIN_` tags are the whole of what it means: `loginDeadIdentity` is the terminal state itself, for the same reason `hasDied` is, while `loginLedgerUnsafe` and `loginIdentityMismatch` are facts about one *connection attempt* and say nothing about the watched agent - read alike they labelled a live, connected agent `no body` and froze its reserve trend, with no per-tick record from a player body able to correct it.
`witnessDisputed` is the sixth, and its six `DISPUTED_` tags cover two entirely different cross-checks: three doubt the *numbers* beside the agent and three doubt *where the agent is*, so `ObserverView.disputedNote` reads the tag and an unrecognised one says only that the server disagreed rather than borrowing either sentence.
Read as one sentence, every movement dispute reached an operator labelled as a vitals or inventory disagreement, which is a wrong statement about the run rather than a vague one.
All of them carry an `EventTag` in `BodyEventRecord.outcome`, `BodyEventJournal.reject`, `recordConversion`, `recordRetreat`, `WitnessJournal.denied` and `WitnessJournal.revived` require it so a new refusal cannot forget to say which it is, and `WatchState`/`TaggedActivity`/`ObserverView` branch on the tag.

**A watch belongs to an observer, not to a sink.**
`WatchCommand.onCommand` builds a fresh `BukkitObserverSink` every time the command is typed, so `Observatory.watch` compares `ObserverSink.observer` - a player's uuid - and not sink identity.
It also *keeps* the standing sink rather than swapping in the fresh one, because only the sink that put a boss bar up can take it down: releasing and repainting would flicker the display, and skipping the release without keeping the old sink would leave an orphaned second bar.
A stale surface (the same account after a reconnect) fails the `isPresent` half of that check and is replaced.
**What is known follows the agent, not the surface.**
A `watch` naming the agent already being watched keeps its `WatchState`, because that state is a projection of the append-only record rather than anything about who was looking; naming a *different* agent starts blank, and so does a watch that was stopped.
Whether the display kept anything is `watch`'s own answer (`WatchAttachment.KEPT` / `FRESH`), and `KEPT` needs two things at once: the standing watch must belong to the asking observer, *and* the view must render something for the state it held - a state that survived without reaching the line is kept exactly as it is and answered `FRESH`.
A takeover is `FRESH` as well, worded exactly as a first watch is, and inherits the displaced watch's state all the same: the operator taking over has lost nothing, and `KEPT` on a first-ever watch would tell them which agent the operator they displaced had been watching, which `WatchStanding.NotMine` refuses to say.
`Observatory.kt` is the authoritative statement of how that answer is reached - on `WatchAttachment` and on `Observatory.watch`'s `@return` - so it is not restated here.
**Every question about a watch is asked as an observer**, for the same reason: `standing` and `stop` both take who is asking and answer as `WatchStanding` (`Mine` / `NotMine` / `Nobody`), so ending a watch and reporting one obey the rule `watch` already does.
`stop` ends the asker's own watch and refuses anybody else's rather than releasing it - a sink is one-way, so the operator who typed the command cannot say anything to the watcher whose bar it would have taken down, and a refusal needs no message because nothing happened.
`NotMine` deliberately names no agent, since which agent somebody else is watching is not part of the run.
`Observatory.shutDown` is the one unconditional way out and exists only for `LoomPlugin.onDisable`, where Loom is going away for everybody and there is nobody to ask on their behalf.

Eight things there are easy to undo by being helpful:

- **The colour follows how much of a vital is left, never which way it is going.** A reserve is spent by living, so "declining" is the standing condition of every living agent rather than news about one: a trend-driven colour turned an in-world run yellow four seconds after the spawn and kept it yellow for the whole of the agent's life, spending the one channel an operator reads at a glance on the fact that time passes. `ObserverView.vitalLevel` is level-only for that reason - half a vital left is `CONCERN`, a quarter is `ALARM` - and is applied to the reserve and to health alike, since either can end the agent. The trend word stays on the *line*, where its absence is the signal: a reserve that is not falling has just been rested, or is frozen because the agent has no body spending it (`WatchState.isReserveFrozen`, which covers a put-away body, a refused spawn, and a body a conversion took, as well as a death).
- **The redaction rule is one total function**, `ObserverView.showsDetail`, and `decided` is its single `true`. Every other event gets the view's own fixed sentence, because a record's `detail` can carry a chunk list, free coordinates, or a provider failure that quotes back the perception or the credential it was given. `ObserverViewTest` sweeps a marker through every event's detail rather than naming today's events, so an event added later is covered the day it is added.
- **`noteFor` is total over `BodyEvent` with no default branch**, for the same reason routing is total over `DecisionImportance`: a new event defaulting into the stream is how a bounded display becomes a firehose.
- **A reading is carried forward, never invented - and the model stamp belongs to one cycle.** `WatchState.advanced` holds the last reading of either vital, the trigger, and the stamp over records that restate none of them, because an agent does not stop having them. The stamp is the only exception, which is why its rules have their own file, `DecisionStamp.kt`, beside `WatchState.kt`: it is dropped *and* refused, and both questions need `WatchState.cycle` - the newest `requestId` a `perceived` record has started - to answer. `stampAfter` drops it at a `cognitionUnavailable` naming the cycle the line is about, which says outright that that cycle has no model, and at a `perceived` naming a *different* request, which has started one no model has answered yet. It also refuses one, because decisions arrive in whatever order the minds answer in and several agents can think in one tick: a `decided` from a superseded cycle would otherwise reattach its model to the current trigger and stay there, wrong from the moment it is shown with no later record to restate it. A `cognitionUnavailable` from a superseded cycle is refused the same way and by the same predicate (`answersTheCycle`, shared with `WatchState.kt`), because it carries the older request's own trigger: read as news it took the answered cycle's model off the line, relabelled the line with the superseded trigger, and reported `mind did not answer` about a cycle that was answered and applied. A watcher with no cycle yet takes the stamp, since it may have attached between a perception and its answer - which fails open, so with several answers in flight the stamp it settles on can be a superseded cycle's until a `perceived` record names a cycle: nothing can order them, because a `requestId` says nothing about when its perception was taken and a `decided` record's tick is the arrival order that is already wrong. Either way a held stamp renders `goal review -> model/prompt tier`, which reads as "this trigger was answered by this model"; the in-flight case is the whole of the wait during a silent mind, and it is a wrong *value* as well as a wrong claim now that a second tier is reached in an ordinary run - a threat sighting is notable or pivotal, and the router gives each tier its own model and prompt version.
- **A world-level record is said to the operator and stops there.** `Observatory.saw` lets `worldHoldFailed` through whoever it is filed under, because an operator needs the caveat on their permadeath figures while watching rather than afterwards in the log - but it may not reach `advanced`, since a record filed under `loom:world` is a fact about the world and every field it carried would be read as the watched agent's own reserve, health, trigger or activity. Today `BodyEventJournal.recordForWorld` carries none, which is the only reason letting it through has cost nothing so far; one field added there would have been silently attributed to whichever agent happened to be watched, so the guard is in `saw` and pinned by a unit regression that fabricates a world record carrying the fields a future one might.
- **There are two bounds, and collapsing them back into one costs the most valuable line on the screen.** `ObserverBound.lineChars` (96) is sized for a boss bar title; `noteChars` (192) is sized for chat. A first in-world run had the mind's reasoning cut in half by the boss bar's width in a chat message that had room for all of it.
- **No line reaches an operator except from `refresh`, and the three methods that do touch the sink are main-thread only.** `saw` runs on whichever thread appended the record and Bukkit is main-thread only, so `saw` accumulates and `refresh` delivers, on the plugin's own timer. That is also where the noise bound and the dropped-watcher check live - a disconnected player is noticed nowhere else. `watch` (which notes a displacement), `stop` and `shutDown` do touch the sink, so they must be called on the main thread; nothing enforces it, and it holds only because each is reached from `WatchCommand.onCommand` or `LoomPlugin.onDisable`. The earlier "only `refresh` touches the sink" was false and is exactly what a future change would trust before calling `watch` from a worker.
- **The queue cap bounds a burst; the duplicate rule bounds a *condition*, and both are needed.** `Watch.offer` drops a note identical to the one before it, and does not count it as skipped, because nothing was lost. Some events recur every tick for as long as something is wrong - a refused world hold is recorded on every `follow` - and queued each time they fill all eight lines with one sentence and evict the `decided` and `died` lines that sentence exists to qualify; counting them as skipped would only trade the duplicates for a running "(N lines skipped)". The comparison is against the last note *taken*, not the queue's tail, so draining at a refresh does not turn a standing condition back into one line per refresh, and only *consecutive* duplicates go, so a condition recurring after real news is stated again.

`WatchState.isFinal` is derived from the activity rather than stored, so the tombstone and the state cannot disagree, and a final state renders no energy trend: a dying agent's last reading is always a falling one, and a live trend would sit on the tombstone claiming something was still happening.

## Verifying a body change

Gates do not cover the process/server boundary; a player-body change is not done until the disposable Paper 1.21.1 path in `DEMO.md` passes.

Use `/loombody create|inspect|think|stop`. The acceptance run must prove:

- registration precedes launch and `create` completes only after control and server readiness;
- one perception/decision/action chain preserves its request id and request-scoped refs;
- a real Mineflayer flight moves the server player, while overlapping movement returns `CONTROL_NOT_READY` without disconnecting or killing the process;
- repeated senses of one server-correlated creature spend the existing threat debounce;
- a low-food player consumes exactly the offered stack and reports vanilla food/saturation;
- killing the child produces `DISCONNECTED`, no tombstone, and a restart with the exact same identity;
- graceful stop closes held sessions, keepalives, workers, listener and child before recording `despawned`;
- only a server `kill` produces one durable `died`, and both `/loombody create` and an independent reconnect remain denied after restart;
- scheduled reviews follow `server.currentTick`: freeze advances none and `/tick sprint` advances the deterministic cadence.

The append-only `plugins/Loom/body-events.jsonl` is the research record and `plugins/Loom/player-deaths.jsonl` is the synchronous authorisation ledger. Before trusting a run, check the Paper log for `body event log` warnings and confirm no `loom-body.js`, cognition, Paper or control-listener process remains.
`research/README.md` is the authority on a run that is kept as an experiment, and its sharpest edge is that a committed experiment's evidence must never be edited or reformatted.
A manifest's shape is a third versioned contract, unrelated to the other two: `research/schema/` holds one frozen schema per generation of the shared core, and `research/schema/README.md` is the whole policy for which changes raise `schemaVersion` and which do not - read it before editing a schema or writing a manifest, and take a new manifest's version from `currentSchemaVersion()` rather than copying the previous run's tag.
The load-bearing rule is that a published generation may only ever be **loosened**, since evidence is committed under it and can never be rewritten to match; the generations are self-contained (no cross-generation `$ref`) so an edit to one cannot redefine another, and no object closes itself with `additionalProperties: false` or `unevaluatedProperties: false`, which is what keeps experiment-specific measurement sections schema-neutral rather than something every generation has to enumerate.

## Gates (fail-the-build from commit 1)

- Rust: `cd cognition && cargo fmt --all --check && cargo clippy --all-targets --all-features -- -D warnings && cargo test`. Lint policy lives in `[workspace.lints]` in `cognition/Cargo.toml` (clippy pedantic/all denied, no unwrap/expect/panic in non-test code, `unsafe_code` forbidden).
- JVM: `cd plugin && ./gradlew check`. Runs detekt + ktlint + ArchUnit + warnings-as-errors compile, none ignoring failures. Build on **Corretto 21** (`jvmToolchain(21)`), Gradle wrapper pinned to 8.14 - which refuses a newer JDK outright, so `./gradlew` failing with nothing but a version number (`* What went wrong: 25.0.3`) means `JAVA_HOME` points at a default JDK that is too new rather than anything being wrong with the build. detekt config: `plugin/config/detekt/detekt.yml` (formatting delegated to ktlint), and the Kotlin line length *both* gates enforce is stated once in the root `.editorconfig`, which records why the two numbers have to stay equal.
  The plugin compiles against a Mojang-mapped server via `paperweight-userdev`; the first build downloads and decompiles it (a few hundred MB, several minutes), and later builds are fast. Paper's runtime is Mojang-mapped, so the jar ships as compiled and is never reobfuscated (`ReobfArtifactConfiguration.MOJANG_PRODUCTION`).
  detekt thresholds are treated as design feedback: clear them by splitting along a real seam rather than by adding suppressions.
- Node (body process and body-control contract): `cd body && npm ci && npm run check`. Runs `standard` lint plus the `node:test` suites; there is no build step, and no network beyond loopback is touched - the suites need no Paper server, no Minecraft account and no credential. **Node 22 or newer**, which `package.json` states and CI's `body` job pins; the process's two dependencies are Mineflayer at an exact `4.38.0` and `mineflayer-pathfinder` at an exact `2.4.5`, with the Prismarine packages a route is measured in arriving transitively and pinned by the lockfile, and the committed `package-lock.json` is deliberately not ignored - `npm ci` fails if it and `package.json` disagree. `test/libraries.test.js` checks the pins against what is *installed* rather than against the lockfile, and pins the pathfinder's own defaults under exactly that version, because a policy that turns thirty-three fields off is only evidence about the library it was measured against. `npm test` runs an explicit `test/*.test.js` glob rather than a directory, which keeps `test/fixtures/` (a fault injector) and `test/harness.js` (the harness three suites drive the body with, from above over a real socket and from below over a fake protocol client) out of the run as suites of their own, and works on Node 25, where a directory positional is `require()`d rather than scanned.
- Node (research manifest schema): `cd research && npm ci && npm run check`. Same discipline as `body` and a separate package - `standard` plus `node:test`, Node 22 or newer, committed lockfile, explicit `test/*.test.js` glob. Every case exercises the real schemas and validator rather than asserting over source text, and the committed manifests it reads are swept off the filesystem so an experiment committed later is covered the day it lands; its one dependency is `ajv` (draft 2020-12), pinned exactly. Ajv `strict` is load-bearing rather than tidy: `strictTypes` refuses a type union unless it is a single type paired with `null`, so a generation cannot be widened into accepting two shapes of one field, and `strictRequired` catches a required field the schema never defines. Each generation compiles on **its own Ajv instance**, because a schema Ajv refuses has already registered its `$id` and a shared instance answers every later call with "id already exists" instead of the real reason.
